Linux iptables Chains: INPUT, FORWARD, OUTPUT
==============================================

How the kernel decides which chain to use
-----------------------------------------

When a packet arrives at a Linux box, the kernel asks one question:

  "Is this packet FOR ME, or am I just passing it along?"

The answer determines everything.


The 3 chains
-------------

INPUT — packets destined for this machine.
  The destination IP matches one of this box's own IPs (ens5, wg0, lo, etc).

  Examples on wg-prod:
    - Someone pings 172.17.65.35 (ens5 IP)          → INPUT
    - SSH connection to the node                      → INPUT
    - WireGuard handshake on UDP 51820                → INPUT
    - Someone pings 172.17.200.2 (wg0 tunnel IP)     → INPUT

  After INPUT, the kernel's local stack processes the packet.
  If it's a ping, the kernel generates a reply → goes to OUTPUT.


FORWARD — packets passing through this machine (it's acting as a router).
  The destination IP is NOT one of this box's IPs. The kernel looks up
  its routing table, finds the outgoing interface, and sends it out.

  Requires: net.ipv4.ip_forward = 1 (otherwise kernel refuses to route).

  Examples on wg-prod:
    - Packet arrives on ens5 dst 10.0.55.10           → FORWARD → out wg0
      (mgmt EC2 trying to reach on-prem nginx)
    - Packet arrives on wg0 from 10.0.50.5 dst 8.8.8.8 → FORWARD → out ens5
      (on-prem host reaching internet via AWS)


OUTPUT — packets generated by this machine itself, going out.
  The local stack created this packet (reply to a ping, initiating SSH, etc).

  Examples:
    - Kernel replies to a ping                        → OUTPUT
    - Node initiates SSH somewhere                    → OUTPUT
    - Node sends a DNS query                          → OUTPUT


The full packet flow
---------------------

INCOMING packet for THIS machine:

  wire → [PREROUTING] → routing decision → [INPUT] → local process
                              ↓
                     "dst IP = my IP?"
                        yes → INPUT
                        no  → FORWARD (if ip_forward=1)

FORWARDED packet (transit):

  wire → [PREROUTING] → routing decision → [FORWARD] → [POSTROUTING] → wire out
                              ↓                                ↑
                     "dst IP ≠ my IP"                   (MASQUERADE happens here)
                     "ip_forward = 1"

OUTGOING packet FROM this machine:

  local process → [OUTPUT] → routing decision → [POSTROUTING] → wire out


Why this matters for TS-NET-006
--------------------------------

The original bug: pinging VPN EC2 (172.17.65.35) from mgmt subnet (172.17.63.30).

  Step 1 — ICMP echo request arrives on ens5.
           dst = 172.17.65.35 (this machine's IP) → goes to INPUT chain.
           INPUT policy ACCEPT, no rules → kernel processes it.

  Step 2 — Kernel generates ICMP echo reply.
           src = 172.17.65.35, dst = 172.17.63.30 → goes to OUTPUT chain.
           OUTPUT policy ACCEPT → allowed.

  Step 3 — Routing decision for the reply: where does 172.17.63.30 go?
           Kernel checks routing table:
             172.17.65.0/24 dev ens5  → 63.30 not in 65.0/24, skip
             172.17.0.0/16 dev wg0   → 63.30 IS in 172.17.0.0/16, MATCH
           Reply goes out wg0 → into the tunnel → on-prem drops it.

  This is why same-subnet (65.x) worked: 172.17.65.0/24 is more specific
  than /16, so ens5 wins the route lookup. Cross-subnet (63.x) had no
  specific route, so the /16 on wg0 hijacked it.

  The fix (changing Address from /16 to /24) removed the 172.17.0.0/16
  connected route. Now the /24 on wg0 only covers 172.17.200.0/24, and
  172.17.63.30 falls to the default route → ens5 → VPC router → test EC2.

  FORWARD chain was never involved in this bug because the packet was
  destined for the VPN EC2's own IP (INPUT path), not transit. The
  FORWARD rules were clean all along — they were the wrong chain to
  investigate.


For transit traffic (the other use case)
-----------------------------------------

When mgmt EC2 pings 10.0.55.10 (on-prem nginx) through the VPN EC2:

  Step 1 — Packet arrives on ens5. dst = 10.0.55.10 (not this machine's IP).
           ip_forward = 1 → kernel decides to forward → FORWARD chain.

  Step 2 — FORWARD chain: rule "-o wg0 -j ACCEPT" matches → allowed.

  Step 3 — Routing: 10.0.55.0/24 dev wg0 → packet goes out wg0 into tunnel.

  Step 4 — POSTROUTING: MASQUERADE on -o ens5 does NOT match (packet goes
           out wg0, not ens5). No NAT applied. Source stays 172.17.63.30.

  Step 5 — On-prem MikroTik receives it. Source 172.17.63.30 is within
           the peer AllowedIPs (172.17.0.0/16). Routes to 10.0.55.10.

  Return: 10.0.55.10 replies to 172.17.63.30. MikroTik routes via tunnel.
          Arrives on wg0, FORWARD rule "-i wg0 -j ACCEPT" matches.
          Routing: 172.17.63.30 → ens5 (after /24 fix). Goes to VPC.
          VPC delivers to mgmt EC2. Ping succeeds.


Why manual ip addr edit broke 10.x but reboot fixed it
-------------------------------------------------------

wg-quick is the tool that brings up wg0. When it runs "wg-quick up wg0",
it does 3 things from wg0.conf:

  1. Creates wg0 interface and assigns Address (with the mask → connected route)
  2. Reads AllowedIPs from each [Peer] and installs routes:
       10.0.5.0/24 dev wg0
       10.0.50.0/24 dev wg0
       10.0.51.0/24 dev wg0
       ... etc
  3. Runs PostUp commands (iptables FORWARD + MASQUERADE rules)

When you manually ran:
  sudo ip addr del 172.17.200.2/16 dev wg0
  sudo ip addr add 172.17.200.2/24 dev wg0

This only changed the address and connected route. It did NOT re-run
wg-quick. The AllowedIPs routes (10.0.x.x dev wg0) were associated with
the old /16 address and got cleaned up when the address was deleted.

Result after manual edit:
  - 172.17.200.0/24 dev wg0    ← new connected route (correct)
  - 10.0.x.x routes            ← GONE (wg-quick never re-installed them)

  ip route get 10.0.55.1 returned "via 172.17.65.1 dev ens5" — the
  default route. AWS doesn't know what to do with 10.0.55.1, drops it.

When you rebooted:
  - systemd starts wg-quick@wg0.service
  - wg-quick reads the EDITED wg0.conf (Address = 172.17.200.2/24)
  - Installs /24 connected route (correct, no /16 hijack)
  - Installs ALL AllowedIPs routes fresh (10.0.x.x dev wg0)
  - Runs PostUp iptables commands
  - Everything works

Lesson: never live-edit wg0 with ip addr commands. Always edit wg0.conf
and bounce with wg-quick down/up (or reboot). wg-quick is the only thing
that keeps the address, routes, and iptables rules in sync.


Quick reference: checking each chain
--------------------------------------

  sudo iptables -L INPUT -n -v       # what's allowed IN to this machine
  sudo iptables -L FORWARD -n -v     # what's allowed THROUGH this machine
  sudo iptables -L OUTPUT -n -v      # what's allowed OUT from this machine
  sudo iptables -t nat -L -n -v      # NAT rules (MASQUERADE, DNAT, SNAT)

  ip route get <destination_ip>       # which interface handles the reply
  sysctl net.ipv4.ip_forward         # is forwarding enabled at all
