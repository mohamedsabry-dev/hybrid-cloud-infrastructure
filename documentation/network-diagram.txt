================================================================================
                         DESIGN DECISIONS & Q&A REFERENCE
================================================================================

This section documents architectural questions raised during design review
and the decisions made, for future reference.

┌─────────────────────────────────────────────────────────────────────────────┐
│ Q1: Why no High Availability (HA) for router, NAS, switches?               │
├─────────────────────────────────────────────────────────────────────────────┤
│ Decision: Single devices acceptable                                        │
│ Reason:                                                                     │
│ ├── Home lab with limited resources (space, power, budget)                 │
│ ├── Usage: Few hours per day, shut down most of the time                   │
│ ├── Focus: Development (Terraform, Ansible, Python), not 24/7 production   │
│ └── Light workloads, not heavy K8s pod traffic                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│ Q2: Why WiFi for management instead of wired VLAN?                         │
├─────────────────────────────────────────────────────────────────────────────┤
│ Decision: WiFi via Access Point on ER605 LAN 3                             │
│ Reason:                                                                     │
│ ├── Limited physical ports on router                                       │
│ ├── Achieves true out-of-band isolation from service network               │
│ ├── WiFi is stable (Access Point ~1 meter from laptops)                    │
│ └── Practical for home lab environment                                     │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│ Q3: Can ER605 handle 14 VLANs + 2 VPN tunnels?                             │
├─────────────────────────────────────────────────────────────────────────────┤
│ Decision: Yes, acceptable for this use case                                │
│ Reason:                                                                     │
│ ├── Light traffic (development, not production workloads)                  │
│ ├── Few hours per day usage                                                │
│ ├── Real hardware experience valuable for learning                         │
│ └── Adds layer of protection vs software-only (pfSense VM)                 │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│ Q4: Why route all inter-VLAN traffic through ER605 (not Proxmox internal)? │
├─────────────────────────────────────────────────────────────────────────────┤
│ Decision: All inter-VLAN routing via ER605                                 │
│ Reason:                                                                     │
│ ├── Matches production pattern (L3 switch/router between layers)           │
│ ├── Centralized firewall rules and policy enforcement                      │
│ ├── Service layer cannot reach Management layer directly                   │
│ ├── Traffic inspection and audit trail                                     │
│ └── Proxmox does L2 bridging only, no internal routing                     │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│ Q5: Why separate storage network on dumb switch?                           │
├─────────────────────────────────────────────────────────────────────────────┤
│ Decision: Isolated 5-port dumb switch for storage only                     │
│ Reason:                                                                     │
│ ├── Don't mix storage/backup traffic with service traffic                  │
│ ├── NFS and backup loads should not impact service VLANs                   │
│ ├── True network isolation (physically separate)                           │
│ └── Matches production storage fabric patterns                             │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│ Q6: Why 2 WANs in Active-Active mode?                                      │
├─────────────────────────────────────────────────────────────────────────────┤
│ Decision: WAN 1 for Prod VPN, WAN 2 for Dev VPN                            │
│ Reason:                                                                     │
│ ├── 2 separate AWS VPN tunnels (one per environment)                       │
│ ├── Each VPN needs dedicated static public IP                              │
│ ├── Clean separation: WAN1/LAN1=Prod, WAN2/LAN2=Dev                        │
│ └── ISP provides 5 static IPs, using 2 for VPNs                            │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│ Q7: Why Mac Mini for monitoring instead of VM inside lab?                  │
├─────────────────────────────────────────────────────────────────────────────┤
│ Decision: Mac Mini (192.168.0.222) on ISP router network                   │
│ Reason:                                                                     │
│ ├── Mac Mini is always on (can monitor even when lab is off)               │
│ ├── Docker Desktop runs Prometheus + Grafana easily                        │
│ ├── External monitoring = independent from lab failures                    │
│ └── Can collect metrics from both servers + all VMs                        │
│                                                                             │
│ Routing TBD: Static route needed on ISP router or Mac Mini                 │
│              to reach 10.0.x.x lab networks via ER605                      │
└─────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────┐
│ Q8: Why /26 subnets instead of /24?                                        │
├─────────────────────────────────────────────────────────────────────────────┤
│ Decision: /26 (62 usable IPs) for all VLANs                                │
│ Reason:                                                                     │
│ ├── Only 8-10 VMs max per subnet                                           │
│ ├── /24 (254 IPs) is wasteful for this scale                               │
│ ├── /29 (6 IPs) too small for 10 VMs                                       │
│ ├── /28 (14 IPs) would work but /26 gives room for growth                  │
│ └── Efficient IP allocation while maintaining flexibility                  │
└─────────────────────────────────────────────────────────────────────────────┘
