================================================================================
                    VLAN & NETWORKING CONCEPTS
================================================================================

This document explains VLAN, trunk ports, and traffic flow concepts used in
this infrastructure. Educational reference for understanding the network design.

================================================================================
                         TRUNK PORTS EXPLAINED
================================================================================

The Confusion:
─────────────────────────────────────────────────────────────────────────────────
"If services are on 10.0.51.x, 10.0.52.x etc, what is 10.0.50.x for? Is it useless?"

Short answer: Yes, 10.0.50.0 becomes useless. We don't need it.

Why:
─────────────────────────────────────────────────────────────────────────────────
10.0.50.0 was the idea of "one service subnet per server."
But when you have multiple VLANs per server, the physical port becomes a TRUNK.

A trunk port:
├── Carries MULTIPLE VLANs
├── Has no IP itself
└── It's just a pipe

================================================================================
                         HOW IT ACTUALLY WORKS
================================================================================

Physical Reality:
─────────────────────────────────────────────────────────────────────────────────

Prod Proxmox Server
        │
Main Ethernet port (NO IP on this port)
        │
Tagged trunk carrying:
├── VLAN 51 traffic (tagged)
├── VLAN 52 traffic (tagged)
├── VLAN 53 traffic (tagged)
├── VLAN 54 traffic (tagged)
└── VLAN 55 traffic (tagged)
        ↓
ER605 LAN1 port (also trunk, NO IP)
        ↓
ER605 creates VLAN interfaces internally:
├── VLAN 51 interface: IP 10.0.51.1 (gateway)
├── VLAN 52 interface: IP 10.0.52.1 (gateway)
├── VLAN 53 interface: IP 10.0.53.1 (gateway)
├── VLAN 54 interface: IP 10.0.54.1 (gateway)
└── VLAN 55 interface: IP 10.0.55.1 (gateway)

Key Points:
├── The physical port carries everything
├── The VLAN interfaces are logical, inside the router
└── Physical port itself has NO IP

================================================================================
                         HIGHWAY ANALOGY
================================================================================

Think of it like a highway:
─────────────────────────────────────────────────────────────────────────────────

Physical cable = highway (no address itself)

Cars on highway = packets
Each car has a color = VLAN tag

VLAN 51 = red cars
VLAN 52 = blue cars
VLAN 53 = green cars

At the destination (ER605):
├── Red cars exit at red gate (VLAN 51 interface 10.0.51.1)
├── Blue cars exit at blue gate (VLAN 52 interface 10.0.52.1)
└── Green cars exit at green gate (VLAN 53 interface 10.0.53.1)

One highway. Multiple lanes. Each lane has its own exit.

================================================================================
                         INSIDE PROXMOX
================================================================================

Each VM is connected to a bridge tagged with its VLAN:
─────────────────────────────────────────────────────────────────────────────────

Proxmox Linux bridges:
├── vmbr51 (VLAN 51 tag) → FreeIPA VM gets 10.0.51.10
├── vmbr52 (VLAN 52 tag) → Vault VMs get 10.0.52.10/11/12
├── vmbr53 (VLAN 53 tag) → K8s masters get 10.0.53.10/11/12
├── vmbr54 (VLAN 54 tag) → K8s workers get 10.0.54.10/11/12
└── vmbr55 (VLAN 55 tag) → NGINX gets 10.0.55.10

How it works:
├── All bridges connect to same physical port
├── Physical port sends all traffic tagged to ER605
├── VM thinks it's on a normal network
├── Proxmox adds the tag when traffic leaves
└── ER605 reads the tag and routes correctly

================================================================================
                         TRAFFIC FLOW EXAMPLE
================================================================================

K8s master (10.0.53.10) needs a secret from Vault (10.0.52.10):
─────────────────────────────────────────────────────────────────────────────────

Step │ Action
─────┼───────────────────────────────────────────────────────────────────────
1    │ Master sends packet to 10.0.52.10
2    │ Default gateway is 10.0.53.1 (ER605)
3    │ Packet leaves master tagged VLAN 53
4    │ Travels through physical cable to ER605
5    │ ER605 receives on VLAN 53 interface
6    │ Checks routing table: 10.0.52.0/24 is on VLAN 52 interface
7    │ Checks ACL: VLAN 53 → VLAN 52 = ALLOW
8    │ Routes packet out VLAN 52 interface
9    │ Packet arrives at Proxmox tagged VLAN 52
10   │ Proxmox delivers to Vault VM (10.0.52.10)

Key Points:
├── Everything happens on same physical cable
├── Tags separate the traffic
└── Router enforces the rules

================================================================================
                         Q1: VIRTUAL INTERFACES IN PROXMOX?
================================================================================

Question: Do You Need Virtual Interfaces Inside Proxmox?
─────────────────────────────────────────────────────────────────────────────────

Answer: Yes, you do. But it's simpler than you think.

What Proxmox Needs:
─────────────────────────────────────────────────────────────────────────────────
You need ONE Linux bridge per VLAN:

vmbr0 → physical port (trunk, no IP, carries all VLANs)

Then either:

OPTION A: VLAN-aware bridge (RECOMMENDED)
─────────────────────────────────────────────────────────────────────────────────
└── Single bridge vmbr0 with VLAN aware enabled
└── Each VM gets assigned VLAN tag directly
└── Proxmox handles tagging automatically

OPTION B: Separate bridge per VLAN
─────────────────────────────────────────────────────────────────────────────────
├── vmbr51 (VLAN 51)
├── vmbr52 (VLAN 52)
├── vmbr53 (VLAN 53)
└── etc...

Option A is cleaner and what Proxmox recommends.

How Option A Works:
─────────────────────────────────────────────────────────────────────────────────
In Proxmox network config (/etc/network/interfaces):

```
auto eno1
iface eno1 inet manual
# Physical port, no IP, just carries traffic

auto vmbr0
iface vmbr0 inet manual
    bridge-ports eno1
    bridge-stp off
    bridge-fd 0
    bridge-vlan-aware yes    ← This is the key setting
    bridge-vids 51-55        ← For prod server
```

Then when creating VM:
├── VM network interface → vmbr0 → VLAN tag: 51
├── VM network interface → vmbr0 → VLAN tag: 52

Proxmox tags the traffic automatically based on VM assignment.
You don't create separate interface per VLAN.
Just one bridge, VLAN-aware, and assign tag per VM.

Management Interface:
─────────────────────────────────────────────────────────────────────────────────
Proxmox itself needs management IP (e.g., 10.0.10.100):

```
auto vmbr0.10
iface vmbr0.10 inet static
    address 10.0.10.100
    netmask 255.255.255.0
    gateway 10.0.10.1
    vlan-raw-device vmbr0
```

This is the ONLY additional interface you create on Proxmox itself.
Everything else is just VM assignments.

================================================================================
                         Q2: CROSS-ENVIRONMENT TESTING
================================================================================

Question: Cross-Environment Testing Via Router Only?
─────────────────────────────────────────────────────────────────────────────────

Answer: Yes. Exactly correct.
You operate at ER605 only. Don't touch Proxmox.

How It Works:
─────────────────────────────────────────────────────────────────────────────────

Normal state (isolated):
├── DENY: all 5X → all 6X (prod cannot reach dev)
└── DENY: all 6X → all 5X (dev cannot reach prod)

Testing state (temporary ACL):
```
# Temporary rule added on ER605
ALLOW: 10.0.63.10 → 10.0.52.10 (dev K8s master → prod Vault)
# Duration: test window only
# Remove after test complete
```

Key Points:
├── Proxmox has no idea this is happening
├── Traffic just routes differently at ER605 level
├── This is exactly how network engineers manage cross-environment access
└── Firewall rule added. Test done. Rule removed. Clean.

================================================================================
                         Q3: VLAN = SUBNET = TAG?
================================================================================

Question: VLAN X = Subnet X + Tag X?
─────────────────────────────────────────────────────────────────────────────────

Answer: Yes. Exactly.
Three things always go together:

Component        │ Example Value │ Description
─────────────────┼───────────────┼─────────────────────────────────────
VLAN ID (tag)    │ 52            │ The tag number on the packet
Subnet           │ 10.0.52.0/24  │ The IP range for that segment
Gateway (VLAN IF)│ 10.0.52.1     │ The ER605 VLAN interface IP

They don't HAVE to match numerically.
But making them match is:
├── Easier to remember
├── Easier to troubleshoot
└── Standard practice in clean designs

VLAN 52 = 10.0.52.0/24 = obvious

Example Flow With All Three:
─────────────────────────────────────────────────────────────────────────────────

Vault VM boots:
├── Gets IP: 10.0.52.10 (from its subnet)
├── Gets GW: 10.0.52.1 (ER605 VLAN 52 interface)
├── Traffic leaves tagged: VLAN 52
├── ER605 receives on VLAN 52 interface
├── Routes based on destination
└── ACL rules applied

The three elements work together as one unit.

================================================================================
                         SUMMARY
================================================================================

Q1: Virtual Interfaces in Proxmox
─────────────────────────────────────────────────────────────────────────────────
Yes, need virtual interfaces, but just ONE VLAN-aware bridge.
Not separate bridge per VLAN.
Plus one management VLAN interface for Proxmox itself.

Q2: Cross-Environment Testing
─────────────────────────────────────────────────────────────────────────────────
Yes, cross-environment testing = ER605 ACL change only.
Proxmox untouched.
Rule added, test done, rule removed.

Q3: VLAN = Subnet = Tag
─────────────────────────────────────────────────────────────────────────────────
Yes, VLAN X = configure subnet 10.0.X.0/24 + tag traffic with VLAN ID X +
gateway 10.0.X.1 on ER605.
All three together = one complete segment.

================================================================================
                         IP ADDRESSING SCHEME
================================================================================

Pattern: 10.0.XY.Z
─────────────────────────────────────────────────────────────────────────────────

X = environment
├── 5 = prod
└── 6 = dev

Y = plane
├── 0 = identity
├── 1 = platform
├── 2 = vault
├── 3 = control (K8s masters)
├── 4 = data (K8s workers)
└── 5 = DMZ

Z = role
├── .1 = gateway
├── .10-.12 = nodes
└── .20+ = LXC containers

Examples:
─────────────────────────────────────────────────────────────────────────────────
10.0.52.10 = Prod (5) → Vault (2) → Node 1 (.10)
10.0.63.11 = Dev (6) → Control (3) → K8s Master 2 (.11)
10.0.51.20 = Prod (5) → Platform (1) → Ansible LXC (.20)
