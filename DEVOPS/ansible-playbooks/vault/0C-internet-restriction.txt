## Overview

This guide documents the pfSense firewall configuration to restrict Vault nodes from accessing the internet while maintaining internal network connectivity.

### Security Policy
- ✅ **Allow:** Internal network communication (10.0.0.0/8, 192.168.0.0/16)
- ❌ **Block:** Internet access for Vault VMs
- ✅ **Allow:** AWS VPC access via VPN (when configured)

### Affected Systems
- Vault Node 1 (vault-01.home.lab) - 10.0.20.191
- Vault Node 2 (vault-02.home.lab) - 10.0.20.192
- Vault Node 3 (vault-03.home.lab) - 10.0.20.193
- Veeam VM (internet-restricted backup server)

## PART A: pfSense Firewall Configuration

This section covers network-level firewall rules on pfSense to restrict internet access.

## Phase 1: Create Firewall Aliases

**Purpose:** Aliases make firewall rules easier to manage by grouping IPs and networks.

### 1.1 Create Restricted VMs Alias

**Location:** Firewall → Aliases → IP

**Configuration:**
- Click **Add**
- **Name:** `SECURE_NO_INTERNET`
- **Type:** Host(s)
- **IPs:** Add the following VMs:
  - Veeam VM
  - Vault Node 1 (vault-01.home.lab)
  - Vault Node 2 (vault-02.home.lab)
  - Vault Node 3 (vault-03.home.lab)
- **Description:** "VMs blocked from Internet"
- Click **Save**

### 1.2 Create Local Networks Alias

**Location:** Firewall → Aliases → IP

**Configuration:**
- Click **Add**
- **Name:** `LOCAL_NETWORKS` (RFC1918)
- **Type:** Network(s)
- **Networks:** Add your internal subnets:
  - `10.0.0.0/8`
  - `192.168.0.0/16`
  - `172.16.0.0/12` (if used)
- **Description:** "Private Internal Networks"
- Click **Save and Apply Changes**

---

## Phase 2: Configure Firewall Rules

**Location:** Firewall → Rules → LAN (or SERVER_VLAN interface)

⚠️ **IMPORTANT:** Rules are processed top-to-bottom. First match wins. Place these rules **ABOVE** the default "Allow All" rule.

### Rule 1: Allow Internal Traffic

**Purpose:** Permit Vault nodes to communicate with internal resources

**Configuration:**
- **Action:** Pass
- **Protocol:** Any
- **Source:** Single Host or Alias → `SECURE_NO_INTERNET`
- **Destination:** Single Host or Alias → `LOCAL_NETWORKS`
- **Description:** "Allow Secure VMs to communicate internally"

### Rule 2: Block Internet Access

**Purpose:** Prevent Vault nodes from accessing public internet

**Configuration:**
- **Action:** Block (or Reject)
- **Protocol:** Any
- **Source:** Single Host or Alias → `SECURE_NO_INTERNET`
- **Destination:** Any
- **Description:** "Block Secure VMs from Internet"

### Traffic Flow Examples

| Scenario | Source | Destination | Rule Match | Result |
|----------|--------|-------------|------------|--------|
| Vault → K8s | 10.0.20.191 | 10.0.20.101 | Rule 1 | ✅ Allowed (internal) |
| Vault → Google DNS | 10.0.20.191 | 8.8.8.8 | Rule 2 | ❌ Blocked (internet) |
| Vault → Jenkins | 10.0.20.191 | 10.0.20.196 | Rule 1 | ✅ Allowed (internal) |

---

## Phase 3: Prevent Inbound Traffic

### 3.1 Verify NAT Port Forwards

**Location:** Firewall → NAT → Port Forward

**Action:** Ensure **NO** rules point to Vault or Veeam IPs

**Security Note:** By default, pfSense blocks all inbound WAN traffic unless explicitly forwarded. If no port forwards exist, the VMs are protected from external access.

## PART B: Vault VM OS Firewall Configuration

This section covers OS-level firewall (firewalld) configuration on Vault VMs for defense in depth.

### Security Philosophy

**Defense in Depth:** Two firewall layers protect Vault
1. **pfSense (Network Layer)** - Blocks internet access (PART A above)
2. **Vault VM OS Firewall (Host Layer)** - Restricts services to 10.0.20.0/24 only

**All services restricted to authorized sources:**
- SSH (port 22) - 10.0.20.0/24 only
- ICMP Echo (ping) - 10.0.20.0/24 only
- Vault API (port 8200) - 10.0.20.0/24 only
- Node Exporter (port 9100) - 10.0.20.186 only (Monitoring VM)
- Vault Raft (port 8201) - Vault nodes only

### Services Protected

| Service | Port | Restricted To | Playbook |
|---------|------|---------------|----------|
| **SSH** | 22/tcp | 10.0.20.0/24 only | 02-vault_fw_check.yml |
| **ICMP Echo** | N/A | 10.0.20.0/24 only | 02-vault_fw_check.yml |
| **Vault API** | 8200/tcp | 10.0.20.0/24 only | 02-vault_fw_check.yml |
| **Node Exporter** | 9100/tcp | 10.0.20.186 only | 02-vault_fw_check.yml |

### Security Benefits

✅ **SSH Protection:**
- Blocks external SSH brute force attacks
- Blocks unauthorized home network devices
- Ansible automation still works (10.0.20.185)
- Mac Mini can SSH via NAT (appears as 10.0.20.222)

✅ **ICMP Protection:**
- Hides Vault nodes from external network scans
- Prevents ICMP flood attacks
- Internal troubleshooting still works
- Essential ICMP types preserved for networking

✅ **Vault Service Protection:**
- API (8200) only accessible from lab network
- Node Exporter (9100) only accessible from monitoring VM
- Raft (8201) only accessible between Vault nodes
- Defense in depth (pfSense + OS firewall)
- Principle of least privilege

### Potential Issues & Solutions

#### Issue 1: Mac Mini Direct Access

**Problem:** Mac Mini (192.168.0.222) not in 10.0.20.0/24
**Solution:** Already resolved with pfSense NAT (appears as 10.0.20.222)
**Status:** ✅ Working

#### Issue 2: AWS VPN Access (Future)

**Problem:** AWS resources won't be able to access Vault
**Solution:** Add AWS CIDR to firewall rules:

```yaml
# Add to 02-vault_fw_check.yml
- name: Allow SSH from AWS VPC
  firewalld:
    rich_rule: 'rule family="ipv4" source address="172.31.0.0/16" service name="ssh" accept'
    permanent: yes
    state: enabled
    immediate: yes

- name: Allow Vault API from AWS VPC
  firewalld:
    rich_rule: 'rule family="ipv4" source address="172.31.0.0/16" port port="8200" protocol="tcp" accept'
    permanent: yes
    state: enabled
    immediate: yes
```

**Best Practice:** Use specific /24 subnets instead of /16
**Status:** ⏳ Pending AWS VPN implementation

#### Issue 3: Path MTU Discovery

**Problem:** Blocking all ICMP breaks Path MTU Discovery
**Solution:** Already implemented - essential ICMP types allowed:
- destination-unreachable (Type 3)
- time-exceeded (Type 11)
- parameter-problem (Type 12)

**Verify:**
```bash
tracepath vault-01.home.lab  # Should show MTU without errors
```

**Status:** ✅ Resolved in playbook

### Rollback Procedure (Emergency)

**Option 1: Temporarily Disable Firewall**
```bash
ssh vault-01.home.lab
sudo systemctl stop firewalld
```

**Option 2: Remove Restrictive Rules**
```bash
# Re-enable default SSH (removes restriction)
sudo firewall-cmd --permanent --add-service=ssh
sudo firewall-cmd --permanent --remove-rich-rule='rule family="ipv4" source address="10.0.20.0/24" service name="ssh" accept'
sudo firewall-cmd --reload
```

**Option 3: Use Ansible Rollback Playbook**
```yaml
---
- name: Rollback Vault Firewall (Emergency)
  hosts: vault
  become: yes
  tasks:
    - name: Enable default SSH service
      firewalld:
        service: ssh
        permanent: yes
        state: enabled
        immediate: yes

    - name: Reload firewall
      command: firewall-cmd --reload
```

### Best Practices

1. **Test in Stages**
   - Run playbook on ONE node first
   - Verify all access still works
   - Then apply to remaining nodes

2. **Keep Emergency Access**
   - Ensure Ansible controller connectivity (10.0.20.185)
   - Keep vCenter console access for emergency
   - Document rollback procedure

3. **Monitor After Changes**
   - Check `/var/log/firewalld` for denied connections
   - Review `journalctl -u firewalld` for errors
   - Test all integrations (K8s → Vault, Jenkins → Vault)

## Phase 4: AWS VPN Integration (Future)

**Context:** When connecting AWS via Site-to-Site VPN (IPsec/OpenVPN), traffic is treated as internal private traffic.

### Configuration Example

| Parameter | Value |
|-----------|-------|
| Home Subnet | 10.0.20.0/24 |
| AWS VPC Subnet | 172.31.0.0/16 |
| Connection Type | IPsec VPN Tunnel |

### Security Approach

✅ **DO:** Use AWS Private IP Range (172.31.0.0/16)
❌ **DON'T:** Use AWS Public IPs

### Implementation Steps

1. Update `LOCAL_NETWORKS` alias to include AWS VPC subnet (e.g., 172.31.0.0/16)
2. Rule 1 automatically allows Vault ↔ AWS communication (internal traffic)

### Important Considerations

⚠️ **Subnet Sizing:**
- **Avoid /16 subnets if possible:** pfSense creates individual table entries which can exhaust resources
- **Prefer /24 or smaller:** Only include necessary IP ranges
- **Principle of Least Privilege:** Don't allow entire AWS VPC if only specific services need access

⚠️ **Kubernetes Pod Networks:**
- If K8s pods use non-NAT'd IPs, add their ranges to allowed networks

## Mac Mini NAT Configuration (192.168.x → 10.0.20.222)

### Problem Statement

**Issue:** Mac Mini (192.168.0.222) on home network cannot access Vault VMs because Vault OS firewall only allows connections from 10.0.20.0/24 subnet.

**Solution:** Create Virtual IP and configure Outbound NAT to translate Mac Mini traffic to appear from 10.0.20.222.

### Step 1: Create Virtual IP

**Location:** Firewall → Virtual IPs

**Configuration:**
- Click **Add**
- **Type:** IP Alias
- **Interface:** LAN (10.0.20.x interface)
- **Address:** 10.0.20.222/32
- **Description:** "VIP for Mac Mini NAT"
- Click **Save and Apply**

### Step 2: Configure Outbound NAT

**Location:** Firewall → NAT → Outbound

**Configuration:**
- **Mode:** Hybrid Outbound NAT (or Manual)
- Click **Add** (up arrow to place at top)

**Rule Configuration:**
- **Interface:** LAN (where traffic exits to Lab)
- **Address Family:** IPv4
- **Protocol:** Any
- **Source:** Network → 192.168.0.222/32 (Mac IP)
- **Destination:** Network → 10.0.20.0/24 (Lab subnet)
- **Translation Address:** 10.0.20.222 (VIP)
- **Description:** "Masquerade Mac as 10.0.20.222"
- Click **Save and Apply**

### Traffic Flow Diagram

```
Mac Mini (192.168.0.222)
    ↓ Sends packet to Vault
pfSense NAT (translates source)
    ↓ Rewrites: 192.168.0.222 → 10.0.20.222
Vault (10.0.20.191)
    ↓ Sees connection from 10.0.20.222
    ✅ Allowed (matches 10.0.20.0/24 firewall rule)
    ↓ Sends reply to 10.0.20.222
pfSense NAT (un-translates destination)
    ↓ Rewrites: 10.0.20.222 → 192.168.0.222
Mac Mini receives reply
```

### Verification

**Command:**
```bash
ssh vault-01.home.lab 'netstat -tn | grep 222'
```

**Expected Output:**
```
tcp  0  0  10.0.20.191:8200  10.0.20.222:62861  ESTABLISHED
tcp  0  0  10.0.20.191:8200  10.0.20.222:5150   ESTABLISHED
tcp  0  0  10.0.20.191:8200  10.0.20.222:5556   ESTABLISHED
```

**Interpretation:** All connections show source IP as 10.0.20.222 (NAT successful)

## Advanced Networking Considerations

### Kubernetes Pod NAT Behavior

**Question:** When a pod inside k8s-worker1 (10.0.20.x subnet) uses a pod network (e.g., 192.168.16.x), will it pass through pfSense?

**Answer:** NO - Traffic is NATed and bypasses pfSense

### Traffic Flow Example

| Step | Layer | Details |
|------|-------|---------|
| **1. Pod Sends Packet** | L3 | Source: 192.168.16.5 (Pod IP)<br>Destination: 10.0.20.191 (Vault) |
| **2. CNI SNAT** | L3 | Source: 10.0.20.101 (Worker Node IP)<br>Destination: 10.0.20.191 (Vault) |
| **3. Layer 2 Switching** | L2 | Both 10.0.20.x → Same subnet<br>Direct switch communication<br>**Does NOT route through pfSense** |

### Network Path Visualization

```
Pod (192.168.16.5)
    ↓ CNI overlay network
Worker Node (10.0.20.101)
    ↓ SNAT/Masquerade (source rewrite)
Layer 2 Switch (10.0.20.x subnet)
    ↓ Direct forwarding (same subnet)
Vault (10.0.20.191)
    ↓ Sees connection from 10.0.20.101

⚠️ pfSense is NOT in this path (Layer 2 vs Layer 3)
```

### Security Implications

| Security Layer | Impact | Control Method |
|----------------|--------|----------------|
| **pfSense Firewall** | ❌ Does not apply | Same-subnet traffic bypasses router |
| **Vault OS Firewall** | ✅ Applies | Restricts to 10.0.20.0/24 (see 02-vault_fw_check.yml) |
| **Kubernetes Network Policies** | ✅ Applies | Pod-to-pod access control |
| **Connection Visibility** | ⚠️ Limited | Vault sees Worker Node IP, not Pod IP |

**Recommended Controls:**
- ✅ Kubernetes Network Policies (pod-level access control)
- ✅ OS-level firewall (iptables/firewalld) on Vault VMs
- ✅ Restrict to 10.0.20.0/24 in Vault firewall (see `02-vault_fw_check.yml`)

## Maintenance Checklist

### When Adding AWS VPN

1. ✅ Update `LOCAL_NETWORKS` alias with AWS VPC subnet
2. ✅ Update `02-vault_fw_check.yml` to allow AWS IPs
3. ✅ Test connectivity after changes
4. ✅ Use /24 or smaller subnets (avoid /16 to prevent pfSense table exhaustion)

### When Adding New Restricted VMs

1. ✅ Add VM IP to `SECURE_NO_INTERNET` alias
2. ✅ Verify firewall rules still ordered correctly
3. ✅ Test both internet block and internal access

### Regular Security Checks

**Monthly Tasks:**
- ☐ Review NAT Port Forwards (should have none for Vault)
- ☐ Verify no unexpected entries in `SECURE_NO_INTERNET` alias
- ☐ Check Vault OS firewall rules (only allow 10.0.20.0/24)
- ☐ Monitor pfSense logs for blocked traffic attempts

**After Infrastructure Changes:**
- ☐ Re-run verification tests (internet block, internal access)
- ☐ Verify Mac Mini NAT still functioning (check netstat output)
- ☐ Confirm Kubernetes pod access still works
