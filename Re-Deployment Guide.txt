================================================================================
                      WORKFLOW LOCK PATTERN
================================================================================

SAFE TRIGGER MECHANISM (workaround for workflow_dispatch limitation):

Lock Variables:
  Pattern: {ENV}_INFRA_{NAME}_LOCK
  Example: DEV_INFRA_FREEIPA_LOCK

Values:
  true  -> Workflow skips execution (safe default)
  false -> Workflow runs on push

To trigger a workflow:
  1. Set variable to "false" in GitHub UI
  2. Push to branch (workflow runs)
  3. Set variable back to "true" (re-lock)

Auto-Lock (golden templates only):
  Golden VM/LXC workflows auto-lock after success.
  Other workflows keep manual control.

                      CODE ARCHITECTURE: COPY-PROMOTE PATTERN
================================================================================

PATTERN CHOSEN: Folder Isolation (Copy-Promote)

  terraform/dev/aws/secrets/     <- DEV code (develop here)
  terraform/prod/aws/secrets/    <- PROD code (copy when ready)

  ansible/dev/playbooks/         <- DEV playbooks
  ansible/prod/playbooks/        <- PROD playbooks

  .github/workflows/dev-*.yml    <- DEV workflows
  .github/workflows/prod-*.yml   <- PROD workflows

--------------------------------------------------------------------------------

WHY NOT SINGLE-SOURCE (shared code + env variables)?

  Problem: If playbooks/terraform are shared, and you're halfway through
  developing a new feature in dev branch, then need to merge OTHER completed
  work to prod - the incomplete work comes along too.

  Example:
    ansible/playbooks/new_feature.yml  <- half-done in dev branch
    # You merge to prod for a different fix
    # Git brings the half-done playbook too

  With folder isolation:
    ansible/dev/playbooks/new_feature.yml   <- half-done, stays in dev
    ansible/prod/playbooks/                  <- clean, only complete work
    # Merge to prod branch - prod folder unaffected
    # Copy new_feature.yml to prod WHEN READY

--------------------------------------------------------------------------------

WHEN TO USE EACH:

  Copy-Promote (our choice):
    + Features take multiple commits
    + Work on many things in parallel
    + Solo developer = you are the gatekeeper
    + Explicit control over what goes to prod

  Single-Source (alternative):
    + Features are atomic (one commit = complete)
    + Strict PR review process with team
    + Feature flags to hide incomplete work

--------------------------------------------------------------------------------

DEV -> PROD PROMOTION WORKFLOW:

  1. Complete and test feature in dev folder
  2. Copy to prod folder, update env-specific values (IPs, tags)
  3. Use diff to verify only expected changes:

     # Terraform
     diff -r terraform/dev/aws/secrets terraform/prod/aws/secrets

     # Ansible
     diff -r ansible/dev/playbooks ansible/prod/playbooks

     # Workflows
     diff .github/workflows/dev-aws-secrets.yml .github/workflows/prod-aws-secrets.yml

  4. Commit and push to prod branch

--------------------------------------------------------------------------------

WHAT SHOULD DIFFER (expected):

  +-- Environment tags: "dev" vs "prod"
  +-- IP ranges: 10.0.6x.x vs 10.0.5x.x
  +-- Secret paths: dev/* vs prod/*
  +-- State bucket/table names: *-dev vs *-prod
  +-- Role names: *-dev vs *-prod
  +-- Branch triggers: dev vs prod

WHAT SHOULD NOT DIFFER (drift = bug):

  +-- Logic/structure of terraform resources
  +-- Playbook tasks and handlers
  +-- Workflow steps (except env-specific values)
