DECISIONS
├── 1. Package Installation Method
│   ├── Decision
│   │   └── How to install the Vault binary on vault nodes
│   ├── Options Considered
│   │   ├── HashiCorp APT repo (Debian/Ubuntu only)
│   │   ├── HashiCorp YUM/DNF repo (RHEL-family)
│   │   └── Direct binary download
│   ├── Chosen
│   │   └── HashiCorp YUM/DNF repo via yum_repository + rpm_key
│   ├── Rationale
│   │   └── Vault nodes run Rocky Linux 10 (RHEL-family). DNF repo
│   │       provides GPG-verified packages, dependency resolution,
│   │       and future upgrade path via dnf update
│   └── Trade-offs
│       └── Requires explicit rpm_key task in addition to yum_repository.
│           Binary download would be simpler but loses package management
│
├── 2. TLS Certificate Source
│   ├── Decision
│   │   └── Which CA to use for Vault node TLS certificates
│   ├── Options Considered
│   │   ├── Keep RPM-generated self-signed placeholder certs
│   │   ├── Generate custom self-signed certs via Ansible
│   │   └── Request IPA-signed certs via Certmonger
│   ├── Chosen
│   │   └── IPA-signed certs via Certmonger (ipa-getcert request)
│   ├── Rationale
│   │   └── All nodes are IPA-enrolled. IPA-signed certs are trusted
│   │       automatically via /etc/ipa/ca.crt. Certmonger handles
│   │       auto-renewal with post-save hook — zero manual rotation ever
│   └── Trade-offs
│       └── Requires FreeIPA service principal creation first.
│           More setup steps than self-signed but eliminates all
│           manual cert rotation permanently
│
├── 3. FreeIPA Service Principal — host/ vs vault/
│   ├── Decision
│   │   └── Whether to create dedicated vault/ principal or reuse host/
│   ├── Options Considered
│   │   ├── Use existing host/vault1.lab.local principal
│   │   ├── Create dedicated vault/vault1.lab.local per node
│   │   └── Skip service principal, use self-signed certs
│   ├── Chosen
│   │   └── Dedicated vault/vault1.lab.local service principal per node
│   ├── Rationale
│   │   └── Isolates cert permissions, enables independent cert lifecycle,
│   │       follows PKI best practice. Cleaner for future Kerberos
│   │       integration with Vault LDAP auth method
│   └── Trade-offs
│       └── Requires 3 extra ipa service-add commands on FreeIPA server.
│           Minor overhead for significant architectural cleanliness
│
├── 4. AWS Credential Injection for KMS Unseal
│   ├── Decision
│   │   └── How to provide AWS credentials to the Vault process
│   ├── Options Considered
│   │   ├── Hardcode in vault.hcl (access_key/secret_key fields)
│   │   ├── EC2 instance profile/IAM role
│   │   ├── Environment variables via systemd EnvironmentFile
│   │   └── HashiCorp vault-env tool
│   ├── Chosen
│   │   └── systemd EnvironmentFile at /etc/vault.d/vault.env
│   │       populated by Ansible template from Ansible Vault encrypted vars
│   ├── Rationale
│   │   └── Hardcoding is a security anti-pattern. Instance profiles
│   │       require EC2 — not available on LXC. RPM-shipped systemd unit
│   │       already references EnvironmentFile=/etc/vault.d/vault.env
│   │       making this the natural integration point
│   └── Trade-offs
│       └── Ansible Vault is a temporary store — planned migration to
│           AWS Secrets Manager once Vault is operational.
│           vault.env must be mode 0600 owned by vault user
│
├── 5. Vault Storage Backend
│   ├── Decision
│   │   └── Which storage backend to use for Vault HA
│   ├── Options Considered
│   │   ├── HashiCorp Consul (traditional HA backend)
│   │   ├── Integrated Raft storage (built-in)
│   │   └── External database (MySQL, PostgreSQL)
│   ├── Chosen
│   │   └── Integrated Raft storage on local-lvm per node
│   ├── Rationale
│   │   └── Raft eliminates need for separate Consul cluster.
│   │       local-lvm provides dedicated isolated storage — running out
│   │       of Raft space will not crash the OS. Simpler operational
│   │       model with no external dependency
│   └── Trade-offs
│       └── NAS/NFS mounts explicitly rejected due to UID remapping
│           complexity in unprivileged LXC. Raft data is node-local
│           by design for consensus
│
├── 6. TLS File Paths
│   ├── Decision
│   │   └── Where to store Vault TLS certificate and key files
│   ├── Options Considered
│   │   ├── /etc/vault.d/tls/ (config directory)
│   │   └── /opt/vault/tls/ (RPM default)
│   ├── Chosen
│   │   └── /opt/vault/tls/ matching the RPM post-install script default
│   ├── Rationale
│   │   └── RPM post-install creates /opt/vault/tls and places placeholder
│   │       certs there. Certmonger overwrites them at the same path.
│   │       IPA CA cert at /etc/ipa/ca.crt referenced directly in
│   │       vault.hcl — no copy needed
│   └── Trade-offs
│       └── Slightly non-standard placement but consistent with RPM
│           conventions. Avoids confusion from certs in two locations
│
├── 7. Vault Initialization — Automated vs Manual
│   ├── Decision
│   │   └── Whether to automate vault operator init in the playbook
│   ├── Options Considered
│   │   ├── Automate in Ansible with idempotency gate
│   │   └── Run manually once on vault1 only
│   ├── Chosen
│   │   └── Manual one-time execution on vault1
│   ├── Rationale
│   │   └── Init is a one-time bootstrap that generates root token and
│   │       recovery keys. Automating risks accidental re-initialization.
│   │       A human must be present to save the recovery keys securely.
│   │       Aligns with: automate repeatable ops, keep one-time sensitive
│   │       operations manual
│   └── Trade-offs
│       └── Not captured in playbook as code. Acceptable because init
│           is genuinely a one-time human action, not a deployment step
│
├── 8. VAULT_ADDR Environment — Per-Session vs Permanent
│   ├── Decision
│   │   └── How to ensure VAULT_ADDR and VAULT_CACERT are available
│   ├── Options Considered
│   │   ├── Set per-command using environment variable prefix
│   │   ├── Add to /root/.bashrc per node
│   │   └── Deploy via /etc/profile.d/vault.sh system-wide
│   ├── Chosen
│   │   └── /etc/profile.d/vault.sh deployed via Ansible copy task
│   │       with inventory_hostname for per-node VAULT_ADDR
│   ├── Rationale
│   │   └── profile.d sourced for all users on every interactive login,
│   │       survives reboots. inventory_hostname ensures each node gets
│   │       its own correct address. VAULT_CACERT=/etc/ipa/ca.crt used
│   │       instead of VAULT_SKIP_VERIFY=1 for proper TLS validation
│   └── Trade-offs
│       └── profile.d not sourced in non-interactive shells (Ansible
│           ad-hoc). For Ansible tasks must source explicitly or use
│           the environment: key in playbook tasks
│
├── 9. Idempotency Gate for Cert Request
│   ├── Decision
│   │   └── How to make ipa-getcert request task idempotent
│   ├── Options Considered
│   │   ├── Check if cert file exists (stat module)
│   │   ├── Check cert issuer (openssl x509 -noout -issuer)
│   │   └── Always run with --force flag
│   ├── Chosen
│   │   └── Check cert issuer with openssl
│   │       when: "'HashiCorp' in cert_issuer.stdout or cert_issuer.rc != 0"
│   ├── Rationale
│   │   └── --force does not exist in installed certmonger version.
│   │       File existence check fails because RPM creates placeholder
│   │       at same path. Issuer check distinguishes HashiCorp placeholder
│   │       from real IPA-signed cert. rc != 0 arm handles missing file case
│   └── Trade-offs
│       └── Requires failed_when: false on check task.
│           Slightly more complex condition — worth it for true idempotency
│
└── 10. Unseal Mechanism — Manual Keys vs AWS KMS
    ├── Decision
    │   └── Which unseal mechanism to use for the Vault cluster
    ├── Options Considered
    │   ├── Standard Shamir secret sharing (manual unseal keys)
    │   └── AWS KMS auto-unseal
    ├── Chosen
    │   └── AWS KMS auto-unseal with recovery keys stored securely
    ├── Rationale
    │   └── Manual unseal requires human intervention every restart.
    │       Unacceptable for a 3-node HA cluster. KMS auto-unseal means
    │       nodes unseal themselves on restart with zero intervention.
    │       Recovery keys only needed if KMS becomes unavailable
    └── Trade-offs
        └── Creates dependency on AWS KMS availability. Mitigated by
            AWS KMS high availability SLA and KMS being in eu-west-2
            matching the dev environment region


ARCHITECTURAL PRINCIPLES APPLIED
├── Manual before automation
│   └── Init kept manual. Repeatable steps automated via Ansible
├── Idempotency first
│   └── Every task designed safe to re-run without side effects
├── Secrets hygiene
│   └── No credentials hardcoded. AWS creds in Ansible Vault encrypted
│       vars, injected via systemd EnvironmentFile
├── PKI integration
│   └── FreeIPA CA for all TLS. No self-signed certs in final state.
│       Certmonger handles auto-renewal
├── Local storage for Raft
│   └── NAS/NFS rejected. local-lvm per node for isolation
├── Zero-touch unseal
│   └── AWS KMS ensures cluster recovers from restarts without intervention
└── Consistent tooling
    └── ansible_freeipa collection for FreeIPA ops.
        Native Ansible modules for OS operations
