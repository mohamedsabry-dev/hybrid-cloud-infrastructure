# DR Task 5: Power Outage Recovery - Issues and Analysis
## Date: 2026-04-09

---

## Background

Before starting DR Test 1, a real electricity outage occurred causing force shutdown of storage and network.
Laptops still had battery and UPS script simulation - at 55% it triggers smooth shutdown.

The script ran automatically on dev server but didn't run on prod.
Figured on prod by manual run - script triggered at 41% and started shutdown.
Suspected wrong config in the cronjob since both servers have the same script.
Electricity recovered after 3 hours.

---

## Issue 1: UPS Monitor Cronjob Misconfiguration

### Observation

**Dev server (correct):**
```bash
root@pve-dev:~# crontab -l
*/5 * * * * /root/scripts/dr_ups_monitor.sh >> /var/log/dr_ups.log 2>&1
0 21 * * 4,6 /root/scripts/backup-proxmox-config.sh >> /var/log/backup-proxmox-config.log
```

**Prod server (incorrect):**
```bash
root@pve-prod:~# crontab -l
0 21 * * 4,6 /root/scripts/dr_ups_monitor.sh >> /var/log/dr_ups.log 2>&1
0 4 * * 0 /root/scripts/backup-proxmox-config.sh >> /var/log/backup-proxmox-config.log
root@pve-prod:~# ps | grep ups
root@pve-prod:~#
```

### Root Cause
Wrong cronjob timing on prod - UPS monitor runs only at 21:00 on Thu/Sat instead of every 5 minutes.

### Fix
Update prod crontab to match dev:
```bash
*/5 * * * * /root/scripts/dr_ups_monitor.sh >> /var/log/dr_ups.log 2>&1
```

## Issue 3 - ROOT CAUSE ANALYSIS

### Symptoms
- WordPress showing "Error establishing a database connection"
- WordPress pods running as 1/1 instead of 2/2 (missing vault-agent sidecar)
- MariaDB pods running correctly as 2/2 with vault-agent sidecar
- /vault/secrets/ directory missing inside WordPress pods

### Investigation Steps

**1. Compared annotations between MariaDB (working) and WordPress (not working):**
- MariaDB had: `vault.hashicorp.com/agent-inject-status: injected`
- WordPress was MISSING this annotation (injection never happened)

**2. Checked Vault Agent Injector status:**
- Injector pod running and healthy
- Webhook registered correctly
- No errors in injector logs

**3. Compared timestamps:**
```bash
kubectl get pod -n apps -l app=wordpress -o jsonpath='{.metadata.name}: Created={.metadata.creationTimestamp} Started={.status.containerStatuses[0].state.running.startedAt}'
```
- WordPress pods Created: 09:00:09Z - 09:00:27Z
- WordPress containers Started: 12:54:09Z - 12:54:11Z
- Vault Injector Started: 12:14:45Z, Ready: 12:14:51Z

**4. Key Finding - Checked etcd backup from 10:40 AM (before outage):**
```bash
ETCDCTL_API=3 etcdctl --endpoints=http://127.0.0.1:2399 get /registry/pods/apps --prefix --keys-only | grep wordpress
/registry/pods/apps/wordpress-85b7f46448-cx2ct   # Different pods!
/registry/pods/apps/wordpress-85b7f46448-dm82c
/registry/pods/apps/wordpress-85b7f46448-nh7hl

ETCDCTL_API=3 etcdctl ... | strings | grep -i "vault-agent"
vault-agent        # OLD pods HAD the sidecar!
vault-agent-init
```

**5. Confirmed:** Old pods (before outage) had vault-agent, current pods do not.
This proves a deployment rollout happened during recovery.

### Root Cause

The Flux Kustomization (`deployments-sync.yaml`) applies BOTH infrastructure and apps in a SINGLE reconciliation with NO DEPENDENCY ordering:

```yaml
# kubernetes/dev/flux/deployments-sync.yaml
path: ./kubernetes/dev/deployments    # Applies everything at once

# kubernetes/dev/deployments/kustomization.yaml
resources:
  - infrastructure   # vault-agent-injector here
  - apps             # wordpress here - NO DEPENDENCY!
```

**When Flux reconciles after cluster recovery:**
1. Flux applies ALL manifests simultaneously
2. Vault HelmRelease triggers -> Injector pod starts spinning up
3. WordPress Deployment triggers -> NEW pods created IMMEDIATELY
4. But Vault Injector isn't READY yet -> pods created WITHOUT sidecar
5. WordPress pods come up as 1/1 (no vault-agent) -> can't get DB password

### Why MariaDB Worked

MariaDB was recreated LATER (64 minutes ago vs 4+ hours for WordPress).
By the time MariaDB StatefulSet was reconciled, the Vault Injector was ready.

| Time     | Event                                            |
|----------|--------------------------------------------------|
| 09:00 AM | WordPress pods created (injector NOT ready)      |
| 11:00 AM | Power outage                                     |
| 12:14 PM | Vault Injector starts and becomes ready          |
| 12:52 PM | MariaDB pod recreated (injector now ready) 2/2   |
| 12:54 PM | WordPress containers restart (same old pods) 1/1 |

### Immediate Fix
```bash
kubectl rollout restart deployment wordpress -n apps
# This forces new pods to go through the now-ready webhook
```

### Permanent Fix

Split Flux Kustomizations with dependency ordering:

1. `infrastructure-sync.yaml` - Deploys infra with healthCheck on vault-agent-injector
2. `apps-sync.yaml` - dependsOn: infrastructure (waits for vault to be healthy)

**Files created:**
- `kubernetes/dev/flux/infrastructure-sync.yaml`
- `kubernetes/dev/flux/apps-sync.yaml`
- `kubernetes/prod/flux/infrastructure-sync.yaml`
- `kubernetes/prod/flux/apps-sync.yaml`

This ensures apps only deploy AFTER vault-agent-injector is healthy.

### Alternative Self-Healing Fix

Add liveness probe to WordPress that checks for vault secrets:

```yaml
livenessProbe:
  exec:
    command: ["test", "-f", "/vault/secrets/db-creds"]
  initialDelaySeconds: 60
  periodSeconds: 10
```

If secrets missing -> probe fails -> pod restarts -> eventually gets sidecar.
