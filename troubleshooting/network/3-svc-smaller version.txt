Prod environment always stable. Investigation ran across 4 phases over 6 days.

  From Dev VMs:
  ping 10.0.6x.1 → From 10.0.60.10 icmp_seq=1 Destination Host Unreachable

  vmbr0: port 1(svc0) entered forwarding state
  vmbr0: port 1(svc0) entered disabled state
  (pattern repeats every 2-3 seconds)

Hardware involved:
  Dev server   → ASUS VivoBook 15 (economy laptop)
  USB adapter  → UGREEN 2.5G (ASIX AX88179B chipset) — single physical chip, multiple ports
  Prod server  → Dedicated laptop with built-in Ethernet on mainboard

Network path (SVC traffic):
  Proxmox Dev (svc0) → FS308GP Port 4 → FS308GP Port 3 → ER605 Port (SVC) → Gateway 10.0.6x.1
  Prod path same structure but via FS308GP Port 5 → ER605 Port 3 — always stable

PHASE 4 | 2026-03-27 | ~1 hr | TRUE ROOT CAUSE IDENTIFIED
_____________________________________________________________________

Checked kernel driver binding on the USB adapter:

Command:
  ethtool -i svc0

Output:
  driver: cdc_ncm   ← WRONG driver

Expected: ax88179_178a  (native ASIX driver for AX88179B)
Actual:   cdc_ncm       (generic CDC NCM fallback)

ethtool svc0 with cdc_ncm driver:
  Speed: 100Mb/s
  Duplex: Unknown! (255)   ← no duplex negotiation
  Auto-negotiation: off
  Link detected: yes

cdc_ncm is a generic USB network driver — does NOT support proper
speed/duplex negotiation. Cannot communicate link parameters to switch
or router. Causes intermittent link flapping when Gigabit negotiation
is attempted because the driver cannot complete the negotiation handshake.

ax88179_178a (native driver):
  Supports full auto-negotiation.
  Reports correct speed and duplex.
  Handles link state properly.

Why cdc_ncm binds instead of ax88179_178a:
  The AX88179B adapter presents itself as a CDC NCM device first.
  Kernel binds cdc_ncm before ax88179_178a can claim the device.
  ax88179_178a module exists in kernel but never gets to bind.

  modinfo ax88179_178a  → module available in kernel
  modprobe ax88179_178a → loaded successfully
  ethtool -i svc0       → still shows cdc_ncm (already bound, too late)

Why Prod is always stable:
  Dev server   → USB adapter (AX88179B) → cdc_ncm (wrong) → broken negotiation → unstable
  Prod server  → built-in mainboard NIC → native driver   → correct negotiation → stable

  Prod defaults to 100M naturally via native driver — never attempted
  Gigabit negotiation with broken cdc_ncm. That is why 100M forced on
  the router side also stabilises Dev — it bypasses the broken Gigabit
  negotiation entirely.

Proposed permanent fix:
  echo "blacklist cdc_ncm" > /etc/modprobe.d/blacklist-cdc_ncm.conf
  update-initramfs -u
  reboot
  ethtool -i svc0  # verify: driver: ax88179_178a

Status: pending reboot test at time of writing.

[Final Root Cause]
ASIX AX88179B USB-Ethernet adapter (UGREEN 2.5G) on Dev server binding to wrong
kernel driver (cdc_ncm) instead of native ax88179_178a. cdc_ncm is a generic USB
network fallback driver that does not support proper speed/duplex negotiation —
reports Duplex: Unknown (255). Causes broken link state communication with switch
and router when Gigabit negotiation is attempted. The adapter presents as CDC NCM
first — kernel binds cdc_ncm before ax88179_178a can claim it.

Forcing 100M on the router side bypasses Gigabit negotiation entirely — cdc_ncm
handles 100M without proper duplex negotiation so the link stabilises.

All other suspected causes across 4 phases were incorrect. cdc_ncm was the
constant underlying problem throughout every phase.

_____________________________________________________________________

[Final Solution]

Working fix (applied):
  Force 100M Full-duplex + Flow Control on all SVC router ports.

  ER605 Port 2  Dev SVC uplink   100M Full-duplex, Flow Control enabled
  ER605 Port 4  Dev SVC backup   100M Full-duplex, Flow Control enabled
  ER605 Port 5  Prod SVC uplink  Auto (100M default, built-in NIC, stable)

  Note: Flow Control alone on Port 4 improved things but did not fix the
  issue — 100M forced is the key setting. Flow Control is additive benefit.

Permanent fix (pending reboot test):
  echo "blacklist cdc_ncm" > /etc/modprobe.d/blacklist-cdc_ncm.conf
  update-initramfs -u
  reboot
  ethtool -i svc0  # verify: driver: ax88179_178a

  If ax88179_178a still unstable at Gigabit → keep 100M forced as permanent.
  If still unstable after driver fix → replace USB adapter with PCIe NIC.

Cleanup required:
  Disable port mirror on ER605 Port 2 — left over from Phase 1 debugging.
  Port mirrors must be removed immediately after debugging sessions.

Verified: Yes (working fix) / Pending (permanent fix)
