# Local kubectl + flux setup (Mac Mini → on-prem cluster)

How I set up my Mac Mini to reach the on-prem Kubernetes clusters from outside Proxmox, so I can run `kubectl` and `flux` commands — especially `flux diff` — as part of my pre-push review loop. Written after adopting `flux diff` during the consolidation-phase review of how Flux actually applies changes to the cluster. The motivation and incident context is in [`../dev/flux/DESIGN.md`](../dev/flux/DESIGN.md) under "flux diff adoption."

> **Known flaw (acknowledged):** this setup uses `admin.conf` on the laptop, which carries an unrestricted superuser identity. I'm aware that's the wrong long-term posture. The intent is to later replace it with a dedicated, RBAC-governed user with read-only permissions — not doing that work now, just acknowledging the gap so a reader doesn't mistake this setup for the target end state.

---

## What this enables

| Command | Why I want it locally |
|---------|----------------------|
| `kubectl get / describe / logs` | Read cluster state without SSH-into-master roundtrip |
| `flux get sources git / kustomizations` | See Flux reconcile status at a glance |
| `flux diff kustomization <name> --path <local>` | **Pre-push validation** — server-side dry-run of my local edits against the live cluster, catches schema / RBAC / enum errors before I commit. Directly addresses the TS-K8S-019 and TS-K8S-042 failure classes (see DESIGN.md) |
| `kustomize build \| kubeconform` | Offline manifest linting (no cluster needed, useful as fallback) |

What I deliberately don't want on the laptop long-term: `apply`, `delete`, `patch`, `create`. Those paths stay in GitOps — either Flux reconciling from git, or GitHub Actions runners with scoped OIDC roles. The laptop is for **reading** state and **validating** proposed changes.

## One-time setup

### 1. Install CLIs

```bash
brew install kubectl
brew install fluxcd/tap/flux
brew install kustomize kubeconform    # optional but recommended — offline validation fallback
```

Check versions:

```bash
kubectl version --client
flux --version
```

### 2. Pull kubeconfig from a master

Two network-side things make this simple on my setup:

- **Mac Mini's IP is explicitly allowlisted into the env VLANs via the MikroTik ACLs** (dev VLAN 61, prod VLAN 51, etc. — see [`../../network/`](../../network/)). The laptop can route directly to the 10.x ranges without VPN gymnastics because that decision was made at the router layer. Any other laptop without that allowlist wouldn't reach the masters — the ACL is the access boundary.
- **Direct root SSH is disabled cluster-wide**, so I SSH as `super_bot` — a FreeIPA domain user with `sudo` privileges equivalent to root — and use `sudo cat` to read the admin kubeconfig. Same pattern I use everywhere else on these nodes.

```bash
# From the Mac Mini, one file per env — keep them separate:
ssh super_bot@10.0.61.10 'sudo cat /etc/kubernetes/admin.conf' > ~/.kube/config-dev
ssh super_bot@10.0.51.10 'sudo cat /etc/kubernetes/admin.conf' > ~/.kube/config-prod

chmod 600 ~/.kube/config-dev ~/.kube/config-prod
```

(Replace the IPs with whichever master is closest / most reliable for you. In my lab, master1 is `*.10` in each env's `/24`.)

### 3. Verify the kubeconfig `server:` URL

The `admin.conf` generated by kubeadm points at the cluster's API endpoint — in my HA control plane that's the **keepalived/HAProxy VIP on port 16443**, not a master's direct `:6443`. Confirm:

```bash
grep server: ~/.kube/config-dev
# expect something like:
# server: https://10.0.61.100:16443
```

If the URL is set to a hostname your Mac Mini can't resolve (e.g. `master1.lab.local`), edit the file and replace with the VIP IP the laptop can actually reach — in my case `https://10.0.61.100:16443` for dev and `https://10.0.51.100:16443` for prod.

### 4. Test reachability + auth

```bash
# Raw TCP + HTTPS health check (should return "ok"):
curl -k https://10.0.61.100:16443/healthz

# kubectl against dev:
export KUBECONFIG=~/.kube/config-dev
kubectl get nodes
# should list all 6 nodes Ready

# flux status:
flux get sources git
flux get kustomizations
# expect flux-system / infrastructure / apps all Ready: True
```

If you see `x509: certificate is valid for ... not 10.0.61.100`, the API server cert doesn't have the VIP IP as a Subject Alternative Name. Either:

- **Quick fix:** add `insecure-skip-tls-verify: true` in the `cluster:` block of the kubeconfig (acceptable for read-only local workflow, NOT for apply commands or CI).
- **Proper fix:** regenerate the API server cert with `--apiserver-cert-extra-sans=10.0.61.100` via kubeadm, restart kube-apiserver on all masters. This is the right thing to do before publish.

### 5. Make KUBECONFIG permanent (not per-session)

By default `export KUBECONFIG=...` only lasts for the current shell. Two ways to make it stick:

**Option A — default to dev + alias for prod (what I do).** Add to `~/.zshrc`:

```bash
# Default KUBECONFIG = dev, so new terminals open with dev selected
export KUBECONFIG=~/.kube/config-dev

# Alias for switching when I need prod
alias kprod='export KUBECONFIG=~/.kube/config-prod'
alias kdev='export KUBECONFIG=~/.kube/config-dev'
```

Every new terminal auto-lands on dev. `kprod` / `kdev` swap within the current shell.

**Option B — merge both configs, switch by context.** The "kubectl-native" way:

```bash
# Merge once:
KUBECONFIG=~/.kube/config-dev:~/.kube/config-prod kubectl config view --flatten > ~/.kube/config
chmod 600 ~/.kube/config

# Rename contexts to something short:
kubectl config rename-context kubernetes-admin@kubernetes dev
# (repeat after merging prod — you'll have a conflict since both came from admin.conf;
#  easier to pre-edit each config-* file and change the context name before merging)

# Then switch with:
kubectl config use-context dev
kubectl config use-context prod
```

I prefer Option A because the two envs are *different clusters* with *different admin identities*, so keeping them in separate files makes it harder to accidentally cross-apply. Option B is cleaner if you have many small contexts.

## Daily workflow — pre-push validation with `flux diff`

My dev-first validate-then-mirror pattern (same as terraform plan-from-dev-only): I run `flux diff` **only against dev**, trust the mirror to reproduce in prod.

```bash
# 1. Edit a manifest locally
vim kubernetes/dev/deployments/infrastructure/vault/helm-release.yaml

# 2. Switch to dev context
kdev

# 3. See what infrastructure would do if I pushed right now:
flux diff kustomization infrastructure \
  --path ./kubernetes/dev/deployments/infrastructure

# Read the output:
#   ✓ unchanged   → no drift, applying would be a no-op
#   ►   drifted   → fields would change, per-field diff shown
#   +   created   → new resource would be added
#   -   deleted   → resource would be pruned (catches accidental deletions)

# If errors (schema, enum, missing field, CRD missing, RBAC) — fix the manifest and re-run.

# 4. When output is clean and matches intent, commit and push
git add -A
git commit -m "vault: bump injector replicas"
git push

# 5. (Optional) Force immediate reconcile to see Flux apply:
flux reconcile kustomization infrastructure
```

Takes ~10 seconds per diff. This is the loop that would have caught:
- **TS-K8S-019** — the restructure-cascade failure. `flux diff` shows `- deleted` lines for every resource a Kustomization rename would orphan, before the rename ever lands in git.
- **TS-K8S-042** — the retry storm. `flux diff` shows the `requiredDuringScheduling` anti-affinity change against the current replica/node count; seeing "would schedule a 4th pod on a 3-worker cluster" is visible *before* the push triggers the retry loop.

Neither ticket would have happened if I'd been running `flux diff` as a habit. That's the lesson — this guide exists to make the habit stick.

## Fallback: offline validation (no cluster needed)

If the Mac Mini can't reach the cluster (VPN down, working offsite, cluster being rebuilt), `kubeconform` catches most of what `flux diff` would catch:

```bash
# Validate manifests against Kubernetes + CRD schemas, no cluster required:
kustomize build ./kubernetes/dev/deployments/infrastructure | \
  kubeconform -summary -strict -verbose

# With Flux's CRDs specifically:
kustomize build ./kubernetes/dev/deployments/infrastructure | \
  kubeconform -summary -strict \
    -schema-location default \
    -schema-location 'https://raw.githubusercontent.com/datreeio/CRDs-catalog/main/{{.Group}}/{{.ResourceKind}}_{{.ResourceAPIVersion}}.json'
```

Catches: schema typos, enum violations (e.g. `sourceRef.kind: "Bukcet"`), wrong apiVersion, missing required fields.
Doesn't catch: what a `flux diff` would show for prune/drift against current cluster state, or RBAC denials.

~90% of `flux diff` coverage without cluster access. Good fallback to have.

## Acknowledged flaw — superuser cert on the laptop

Using `admin.conf` directly means the cluster identifies me as an unrestricted superuser identity, not a normal user governed by RBAC. That's a weakness I'm choosing to live with during this phase because the laptop is the only operator surface, but it is a flaw and I want it recorded as such rather than glossed over.

Intent for later: replace the `admin.conf` copy on the laptop with a dedicated, RBAC-governed user scoped to read-only operations (`get` / `list` / `watch` / `logs`), and keep any mutating paths off the laptop entirely — those stay in GitOps (Flux reconciling from git) or scoped CI roles (GitHub Actions via OIDC). Not implementing this yet; just logging the target so the gap between current state and target state is explicit.
