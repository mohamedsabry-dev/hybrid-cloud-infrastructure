# Flux layer — design notes and reasoning

Why Flux here is split into `infrastructure` + `apps` instead of one Kustomization, why the infra Kustomization has a health check pinned to `vault-agent-injector`, why the Flux controllers themselves carry a pod anti-affinity patch, and why I deliberately do *not* set a priorityClass on them. The story is the same for dev and prod — only the branch ref (`prod` here) and watched path (`./kubernetes/prod/flux` here) differ.

---

## Layout

```
kubernetes/<env>/flux/
├── flux-system/                  # Flux controllers themselves
│   ├── gotk-components.yaml      # generated by `flux bootstrap` — DO NOT edit
│   ├── gotk-sync.yaml            # generated — pins the env's branch + watched path
│   ├── flux-pod-anti-affinity.yaml   # my patch — spreads flux pods across nodes
│   └── kustomization.yaml        # stitches the above together with `patches:`
├── infrastructure-sync.yaml      # Flux Kustomization → deployments/infrastructure/
├── apps-sync.yaml                # Flux Kustomization → deployments/apps/, dependsOn: infrastructure
└── kustomization.yaml            # includes flux-system + the two sync Kustomizations
```

The Flux controller watches `./kubernetes/<env>/flux` by default (set in gotk-sync.yaml). Everything below that path is the cluster's declared state for the env.

---

## Why `infrastructure` + `apps` instead of one Kustomization

The original layout was a single `deployments-sync.yaml` pointing at one big `deployments/` folder. That worked until I hit the race condition documented in [`../../../troubleshooting/kubernetes/12-flux-kustomization-crd-dependency-failure.md`](../../../troubleshooting/kubernetes/12-flux-kustomization-crd-dependency-failure.md). The short version: Flux would apply a HelmRelease that expected a CRD to already exist, but the CRD was being installed by a sibling chart in the *same* Kustomization, and Flux's single-apply ordering didn't guarantee CRD-first. The reconcile would fail, retry, sometimes succeed, sometimes not — classic race.

The fix is dependency ordering at the Flux Kustomization layer, not inside Kustomize. Split the content into two folders and mark the app layer as `dependsOn: infrastructure`:

- `infrastructure/` — CRDs, operators, storage classes, CSI driver, Vault, ingress-nginx, kube-prometheus-stack
- `apps/` — everything that consumes what infra provides (WordPress, Grafana, etc.)

Now Flux reconciles infrastructure first, waits for it to report `Ready: True`, *then* starts on apps. The race goes away because the thing the apps depend on is guaranteed to exist before apps are touched.

## The transition itself nearly took the cluster down

Splitting `deployments-sync.yaml` into two sync files *while `prune: true` was set* is exactly how you delete everything Flux owns. That's the lesson from [`../../../troubleshooting/kubernetes/19-flux-kustomization-restructure-cascade-failure.md`](../../../troubleshooting/kubernetes/19-flux-kustomization-restructure-cascade-failure.md). Flux tracks ownership by the Kustomization's `metadata.name`; when I renamed it while prune was active, Flux saw the old-named resources as "no longer owned by the new-named Kustomization in Git" and started tearing them down. I caught it quickly and recovered, but the near-miss was enough to make me write the operation down properly.

The corrected procedure lives in [`../../docs/flux-restructuring-operation-guide.md`](../../docs/flux-restructuring-operation-guide.md) — disable prune first, do the rename, let Flux re-adopt, *then* re-enable prune. That file is the how-to; this file is the why.

## Why `healthChecks` points at vault-agent-injector

When Flux reconciles `infrastructure` and the apply succeeds, Flux's default definition of "ready" is "all the manifests applied without error." That is not the same as "the things my apps depend on are actually usable." Almost every workload in this cluster has a `vault.hashicorp.com/agent-inject` annotation on it — if `vault-agent-injector` isn't healthy, pods come up without their secrets, silently, and then crash later in whatever application-layer way their missing config manifests as.

So I added an explicit `healthChecks` on the infrastructure Kustomization pointing at the `vault-agent-injector` Deployment in the `vault` namespace. Now:

- Manifests applied but injector not healthy → `infrastructure` stays `Ready: False`
- `apps` depends on `infrastructure`, so `apps` is blocked
- Flux's status makes the problem visible *at the layer where it is*, instead of letting it cascade into opaque app failures

This design also came out of TS-19's aftermath — the cascade exposed how silent Flux's default readiness signal really is. The health check is cheap insurance against "green Flux, broken platform."

## The flux-pod-anti-affinity patch

Out of the box, `flux bootstrap` drops the four controllers (source, kustomize, helm, notification) with no affinity rules. On a 3-master-3-worker cluster that means Kubernetes can pile all four controllers on a single node, and losing that node costs you all of Flux simultaneously. Rescheduling then happens in parallel and takes longer than if the pods had been spread in the first place.

The fix is `flux-pod-anti-affinity.yaml` — a Kustomize patch against each of the four Deployments that sets `preferredDuringSchedulingIgnoredDuringExecution` pod anti-affinity keyed on `app.kubernetes.io/part-of: flux` with `topologyKey: kubernetes.io/hostname`. "Preferred" not "required" on purpose: in a degraded 2-node scenario I'd rather Flux runs co-located than not run at all.

I applied it as a patch rather than editing `gotk-components.yaml` directly because `gotk-components.yaml` is regenerated by `flux bootstrap` on upgrade — any direct edits I made would get silently blown away the next time I ran bootstrap. The patch pattern survives upgrades. The how-to for this pattern is [`../../docs/flux-patch-operation.txt`](../../docs/flux-patch-operation.txt).

## Why there's no priorityClass patch

I checked `gotk-components.yaml` before writing the anti-affinity patch and noticed the default already sets `priorityClassName: system-cluster-critical` on the controllers. That's the highest-priority built-in class — above every normal workload and above the cluster's default scheduling. If the cluster is under resource pressure and the kubelet starts evicting pods, Flux is effectively last to go, which is what I want because without Flux I can't recover the cluster from Git. So there's nothing for me to patch here — the upstream default is correct.

## Branch pinning — dev watches dev, prod watches prod

`gotk-sync.yaml` pins each env's `GitRepository` to the matching git branch (`ref.branch: dev` in dev, `ref.branch: prod` in prod) and the Flux Kustomization's path to `./kubernetes/<env>/flux`. That's the default `flux bootstrap --branch <env>` layout and I didn't change it. The implication is that promotion from dev to prod is a git operation — merge or mirror from the dev branch to the prod branch — not a config change in Flux.

This is intentional: I want the env boundary to be a git boundary, not a flag-in-a-file boundary, because git boundaries are reviewable.

## `flux diff` adoption — the pre-push safety net

The Kustomization split and the `vault-agent-injector` health check addressed two of the three incident classes. The third — TS-K8S-042's retry storm — was not structural; it was a *review gap*. The commit that triggered it (a `requiredDuringScheduling` anti-affinity change on Grafana with 3 replicas on 3 workers) was syntactically fine, schema-valid, and passed every automatic check. The failure only manifested once Flux tried to reconcile and discovered there was no room to schedule a 4th pod during rollout — at which point the retry loop took out the control plane.

During the consolidation phase, going back through the Flux apply flow step by step (source-controller → kustomize-controller's dry-run then apply → helm-controller → notification-controller), I realized the kustomize-controller's internal dry-run is exactly the same thing the `flux diff` CLI exposes — and it runs against the *live* cluster. Every class of failure that the apply path would surface on a real reconcile, `flux diff` surfaces on my laptop *before* I commit:

- Schema typos, wrong enum values, missing required fields — 422 dry-run error shown pre-commit
- Accidental deletions (prune would remove resources I didn't intend to drop) — shown as `- deleted` lines per resource
- Field-level drift (replicas, affinity rules, resource limits) — shown as `►  drifted` with a per-field diff
- Effects that depend on cluster state (an anti-affinity that has no room to schedule) — surfaced as a dry-run admission failure because the scheduler can't place the new pod

Both TS-19 and TS-42 would have been caught by a 10-second `flux diff` before the commit that caused them. That's the habit this tool enables, and the reason I adopted it mid-consolidation even though it wasn't my original plan.

Setup and workflow: [`../../docs/local-kubectl-flux-setup.md`](../../docs/local-kubectl-flux-setup.md). I run it from the Mac Mini against the dev cluster only — same pattern as `terraform plan` from dev only; prod inherits the change via the mirror pass.

## What Flux does *not* save me from

1. **StatefulSet + PVC manual cleanup.** Flux's prune will delete a StatefulSet, but the PVCs its pods claimed stay bound by design (Kubernetes policy, not Flux's). If I restructure a stateful workload and don't manually clean up the PVCs, the next deploy comes up with the old volume attached. Flux can't help me here — the PVC lifecycle is a k8s-layer concern.

2. **Dependency chains *inside* a single Kustomization folder.** Flux applies everything in one folder in a single kustomize build. Kubernetes' own scheduling enforces a few basics (Namespaces before the resources in them, CRDs before the custom resources that use them) but beyond that there's no in-folder ordering. If two resources in the same folder need to come up in order, I have to either split them into separate Kustomizations with `dependsOn`, or accept the retries.

3. **Two conflicting edits in the same commit.** This is the lesson from [`../../../troubleshooting/kubernetes/42-flux-retry-storm-cluster-outage.md`](../../../troubleshooting/kubernetes/42-flux-retry-storm-cluster-outage.md) — a `requiredDuringScheduling` anti-affinity change on Grafana (3 replicas, 3 workers, no room for a 4th pod during rollout) turned a routine reconcile into a stuck HelmRelease, which turned into an aggressive Flux retry loop, which hammered etcd into leader-election storms, which brought the control plane down. Flux is not smart about its own backoff when a reconcile is genuinely unsatisfiable — it just keeps trying. The takeaway I wrote into my own process: every change that will cause Flux to reconcile should be pre-reviewed with the expected loop in mind. "What does Flux do if this fails? How hard does it retry? Does the retry touch etcd?"

4. **Secret contents.** Flux applies manifests; it doesn't render secrets. Secrets here come from the Vault Agent Injector annotation path (infrastructure layer) — Flux brings the manifest, the injector brings the values at pod creation time. If I had Flux manage secrets directly I'd be back to committing them to git.
