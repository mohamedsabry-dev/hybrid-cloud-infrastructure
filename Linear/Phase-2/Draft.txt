SRE-8 Phase 2 - Setup Proxmox Server & Infrastructure Foundation
================================================================================

## Description

Phase 2 focuses on setting up the Proxmox physical host, configuring the
foundational infrastructure services (Zone C - Master Infrastructure), and
establishing the AWS IAM / CI/CD pipelines that support Terraform-driven
provisioning.

Key decision: Migrated from Proxmox 8.4 to 9.1 for container improvements,
Terraform provider compatibility, and better performance. Shutdown the old
environment completely and started fresh on a dedicated NVMe 2TB drive
(dual-boot beside Windows, not on top of it). Boot issue on 8.4 was resolved
by disabling the GPU before migration.

Sub-Issue 3a: Local Terraform Plan Setup (Dev Feedback Loop)
--------------------------------------------------------------------------------

Problem:
  No way to test Terraform code without pushing to GitHub. Every typo or
  missing variable required a full push -> workflow run -> read logs -> fix ->
  push again cycle. This made development painfully slow.

Solution:
  Created a read-only IAM user (dev-plan) for local terraform plan/validate.
  The pipeline still gates all applies. This matches how real teams work:
  local plan for fast feedback, CI/CD for actual deployment.

What was done:

  1. Added IAM user to CloudFormation (roles.yaml)
     - Resource: DevPlanUser (AWS::IAM::User, UserName: dev-plan)
     - Location: cloud/aws/iam/cloudformation/roles/roles.yaml
     - Three policies attached (all reused, nothing new):

     | Policy                              | Why                              |
     |-------------------------------------|----------------------------------|
     | HybridCloud-TerraformStatePolicy-Arn| Read state from S3 + DynamoDB    |
     | HybridCloud-ProxmoxSecretRead-Arn   | Fetch Proxmox API token          |
     | arn:aws:iam::aws:policy/ReadOnlyAccess | Query existing resources during plan |

     This user can read and plan but CANNOT create, modify, or destroy
     any infrastructure.

  2. Deployed the CloudFormation stack update
     - Pushed roles.yaml change to branch
     - Merged to main to trigger CloudFormation git sync
     - Stack updated successfully, dev-plan user created

  3. Created access keys in AWS Console
     - IAM -> Users -> dev-plan -> Security credentials -> Create access key

  4. Configured local AWS CLI profile
     - Command: aws configure --profile dev-plan
     - Region: eu-west-2
     - Credentials stored in ~/.aws/credentials (local only, not in repo)

  5. Created plan.sh script at repo root
     - Sets AWS_PROFILE=dev-plan
     - Fetches Proxmox API token from Secrets Manager automatically
     - Runs terraform init + validate + plan
     - Uses local provider mirror (~/.terraform.d/providers-mirror), no downloads
     - Usage:
         ./plan.sh on-premise/terraform/proxmox/prod
         ./plan.sh cloud/aws/bootstrap/terraform/audit
         ./plan.sh cloud/aws/bootstrap/terraform/secrets

  6. Verified the setup
     - Ran ./plan.sh on-premise/terraform/proxmox/prod
     - Successfully: init from mirror, validated, planned, queried Proxmox
     - No changes needed (infrastructure matches config)

Workflow before vs after:

  Before: Write code -> push -> wait for Actions -> read logs -> fix -> push
  After:  Write code -> ./plan.sh -> see errors instantly -> fix -> push once

Sub-Issue 3b: Dev/Prod Proxmox Separation (Future)
--------------------------------------------------------------------------------

Problem:
  The dev-plan IAM user can read the Proxmox API token, and that token
  (terraform@pve, privsep=0) has full access to Proxmox. This means local
  terraform apply works against production. In a team setting, devs shouldn't
  have unrestricted access to the production environment.

Planned approach:
  Create a dev environment on Proxmox with its own user, token, resource pool,
  state file, and secret. Local development uses dev, pipeline uses prod.

  | Component          | Dev                          | Prod                          |
  |--------------------|------------------------------|-------------------------------|
  | Proxmox user       | dev-terraform@pve            | terraform@pve                 |
  | Resource pool      | Limited (~6 GB nested server)| Full infrastructure           |
  | API token secret   | infra/proxmox/dev-api-token  | infra/proxmox/api-token       |
  | TF state key       | proxmox/dev/terraform.tfstate| proxmox/prod/terraform.tfstate|
  | Used by            | plan.sh (local)              | tf-proxmox.yml (pipeline)     |

Open questions (needs thinking):
  - Dev/prod separation cascades beyond Terraform:
    - Separate VLAN/subnet for dev traffic vs prod traffic
    - Separate PfSense firewall rules per environment
    - DNS naming convention (*.dev.lab.local vs *.lab.local?)
    - How does this fit into the existing network topology design?
  - This is really a network architecture decision, not just a Terraform task.
    Revisit after Sub-Issue 5 (network topology documentation) has some shape.

Status: ON HOLD - let the idea settle before committing to an approach.

Prerequisites (Proxmox host-level, manual or Ansible):
  - [ ] Create isolated network bridge/VLAN on Proxmox for dev traffic
  - [ ] Assign dev subnet (e.g., 10.x.x.x/24) to the new bridge
  - [ ] Carve out storage for dev (ZFS dataset or directory from the 1.7 TB NVMe)
  - [ ] Create nested dev VM (~6 GB RAM) attached to the isolated network
  - [ ] Configure PfSense rules to isolate dev from prod traffic

Tasks (draft, not final):
  - [ ] Design dev/prod network separation (VLANs, subnets, firewall rules)
  - [ ] Create dev-terraform@pve user on Proxmox with limited role
  - [ ] Create a dev resource pool on Proxmox with capped RAM/CPU
  - [ ] Store dev API token in AWS Secrets Manager (infra/proxmox/dev-api-token)
  - [ ] Add IAM policy for dev token read (or reuse ProxmoxSecretRead with wider scope)
  - [ ] Create on-premise/terraform/proxmox/dev/ module with dev backend key
  - [ ] Update plan.sh to point to dev environment by default
  - [ ] Test: local apply creates VM in dev pool, does not touch prod
