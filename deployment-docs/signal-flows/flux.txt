developer pre-push validation (optional but recommended — see kubernetes/docs/local-kubectl-flux-setup.md):
  laptop kubeconfig → flux diff kustomization <name> --path <local-path>
        └─► kustomize build (local) → sends each resource to API server with ?dryRun=All
              ├── API server runs: RBAC → admission webhooks → schema validation (CRD OpenAPI, enums, required fields)
              └── returns: ✓ unchanged / ►  drifted / + created / - deleted (pruned) / 422 validation error
                    → catches schema typos, wrong enums, accidental prunes BEFORE the commit
                    → same validation path the real reconcile would hit (STEP 3 below)
                    → habit that would have prevented TS-K8S-019 and TS-K8S-042

git push
  └─► GitHub stores commit (new SHA assigned)
        └─► source-controller polls (1m) via SSH deploy key
              ├── same SHA → skip, wait next interval
              └── new SHA → pulls repo → verifies → creates Artifact (SHA + checksum + local path)
                    └─► kustomize-controller sees new Artifact
                          └─► dependency check (dependsOn):
                                ├── apps blocked until infrastructure READY: true
                                └── infrastructure proceeds first
                                      └─► for each Kustomization in order:
                                            ├── STEP 1: fetch Artifact → extract configured path only
                                            ├── STEP 2: kustomize build → walk folder tree recursively → resolve resources → apply patches → produce ONE flat manifest stream
                                            │           resources then SORTED for safe apply:
                                            │             1. Namespace
                                            │             2. CustomResourceDefinition + ServiceAccount + Secret + ConfigMap + StorageClass
                                            │             3. ClusterRole / ClusterRoleBinding / Role / RoleBinding
                                            │             4. Service / Deployment / StatefulSet / DaemonSet / Pod / ...
                                            │             5. Everything else (HelmRepository, HelmRelease, custom resources) — arbitrary order
                                            │           NOTE: sort handles hard dependencies (Namespace before namespaced resource, CRD before custom resource).
                                            │                 Soft references (HelmRelease → HelmRepository) rely on controller retries, not sort.
                                            ├── STEP 3: DRY-RUN all resources first (atomic validation gate)
                                            │           for each resource: PATCH ?dryRun=All → API server runs RBAC + admission webhooks + schema validation
                                            │           if ANY resource fails dry-run → STOP, report ValidationFailed, apply NOTHING this cycle
                                            │             → atomic failure: no partial state, prior resources from past reconciles untouched
                                            │             → catches: CRD schema typos, wrong enum values, missing required fields, RBAC denials, missing CRDs
                                            │             → this is what `flux diff` exposes pre-push
                                            │           if all dry-runs pass → proceed to STEP 4
                                            ├── STEP 4: REAL apply → per resource: PATCH → API server writes to etcd → stamp ownership labels:
                                            │             kustomize.toolkit.fluxcd.io/name: infrastructure
                                            │             kustomize.toolkit.fluxcd.io/namespace: flux-system
                                            │           edge case: dry-run pass but real apply fails (webhook drift, quota) → partial apply:
                                            │             resources before failure remain in etcd; resources after are skipped
                                            ├── STEP 5: prune (if true) → delete any resource previously in inventory but not in current build
                                            │           WARNING: rename Kustomization + prune:true = mass deletion (TS-K8S-019)
                                            │           SAFETY: `flux diff` shows `- deleted` lines for every prune target BEFORE commit
                                            ├── STEP 6: healthCheck (if defined) → wait until listed resource reports Ready → timeout → mark not READY
                                            │           WARNING: healthCheck on deleted resource = deadlock forever
                                            │           PATTERN: infrastructure has healthCheck on vault-agent-injector (apps depend on it at runtime)
                                            └── STEP 7: update status
                                                  ├── READY: true  → unblocks dependsOn children
                                                  └── READY: false → children remain blocked
                                                        → if failure is unsatisfiable (e.g. requiredDuringScheduling with no room),
                                                          Flux retries every `interval` without smart backoff → control-plane pressure
                                                          WARNING: TS-K8S-042 retry storm — suspend Flux first, fix the manifest, then resume
                                                        └─► helm-controller (parallel, watches HelmRelease objects):
                                                              ├── source-controller polls HelmRepository (1h) → downloads chart → Artifact
                                                              ├── helm-controller fetches chart Artifact → renders with values block
                                                              ├── no release exists → helm install
                                                              ├── release exists + changed → helm upgrade
                                                              ├── nothing changed → no-op
                                                              └── HelmRelease deleted (by prune) → helm uninstall → ALL resources gone (TS-K8S-019)
                                                                    └─► notification-controller:
                                                                          ├── watches all Flux objects for status changes
                                                                          ├── Alert + Provider configured → sends to Slack/Teams/GitHub
                                                                          └── receives GitHub webhook → triggers immediate reconcile (bypasses poll interval)

every 5m (interval) — even with no git change:
  └─► kustomize-controller re-runs full cycle (STEPS 1-7) → drift correction
        ├── manual kubectl edit → Flux reverts on next reconcile (diff detected, re-applied)
        ├── manual kubectl delete → Flux recreates on next reconcile (prune hasn't fired; resource still in build)
        └── manual kubectl apply (no ownership label) → Flux ignores, resource stays unmanaged

flux manages itself:
  └─► gotk-sync.yaml (root) → flux-system Kustomization watches ./kubernetes/<env>/flux
        └─► finds infrastructure-sync.yaml + apps-sync.yaml → creates those Kustomization objects
              └─► patches in kustomization.yaml merge onto gotk-components.yaml
                    └─► Flux configures its own controllers (replicas, anti-affinity) via GitOps

emergency break-glass (when Flux retry is actively hurting the cluster — TS-K8S-042):
  flux suspend kustomization --all && flux suspend helmrelease --all -A   ← stop retries first
  → diagnose (kubectl/crictl if API server struggling)
  → fix the manifest in git, push
  → flux resume kustomization --all --- verify one Kustomization at a time
