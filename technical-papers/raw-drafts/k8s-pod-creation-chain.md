K8s Pod Creation — From Manifest to Vault-Injected Running App
================================================================

Traces the full path from a Deployment manifest hitting the API
server to a functional, secret-injected pod serving traffic.
Covers every K8s component involved: API server gates, controller
manager, mutating webhook (vault injector), scheduler, kubelet,
init containers, probes, and service endpoint registration.
Includes the Vault trust foundation, two separate TLS handshakes,
and the StatefulSet variation.

For DNS resolution during this flow, see coredns-resolution-chain.md.
For NFS storage provisioning, see nfs-k8s-pv-trace.md.
For Vault TLS certificates and KMS unseal, see vault-unseal-kms-chain.md.


### The K8s ↔ Vault Trust Foundation

before any pod can fetch secrets, a one-time trust setup connects
the K8s cluster to the Vault cluster. same pattern as GitHub ↔ AWS
OIDC (see oidc-terraform-trust-chain.md):

    GH ↔ AWS (OIDC)                     K8s ↔ Vault
    ─────────────────────────────────────────────────────────────
    AWS creates OIDC provider            Vault enables kubernetes auth
    "I trust GitHub"                     "I trust this K8s cluster"
    GitHub sends JWT (repo, branch)      Pod sends JWT (SA, namespace)
    AWS validates via OIDC endpoint      Vault validates via TokenReview API
    AWS returns temp creds (1h)          Vault returns temp token (TTL)
    Creds scoped by IAM policy           Token scoped by Vault policy

the trust playbook runs on k8s-master1 and collects 4 things:

    1. cluster API endpoint (https://10.0.51.100:16443)
         the VIP of the K8s API — where Vault calls back to verify pods

    2. K8s CA cert (/etc/kubernetes/pki/ca.crt)
         K8s internal CA, generated by kubeadm, nothing to do with FreeIPA
         Vault needs this to trust K8s API's TLS cert during TokenReview

    3. vault-auth token (duration=30000h ≈ 3.4 years)
         Vault's ID card to present to K8s when calling TokenReview
         belongs to vault-auth SA in kube-system with system:auth-delegator
         permission to review other pods' tokens
         long-lived by design — can only be captured at creation time

    4. issuer (https://kubernetes.default.svc.cluster.local)
         embedded in every K8s JWT in the iss field
         Vault checks: does the issuer match what I expect?
         disable_iss_validation=false means DO validate it

these 4 are written into Vault:

    vault auth enable kubernetes
    vault write auth/kubernetes/config
      kubernetes_host    = k8s API endpoint
      kubernetes_ca_cert = k8s CA cert
      token_reviewer_jwt = vault-auth token
      issuer             = issuer URL

    vars_prompt for vault admin token in the playbook is intentional —
    human-in-the-loop one-time operation. private: yes means no echo,
    no log.


### Per-App Vault Setup

for each new app that needs secrets, a script handles the
repeatable part (/opt/vault/scripts/vault-pod-setup.sh):

    prompts for: app name, namespace, service account, secret key/values
    creates:
      +-- secret/<app-name>/config — the KV secret in Vault
      +-- <app-name>-policy — read-only access to that secret path
      +-- <app-name> role in auth/kubernetes — bound to the SA + namespace

then the app's deployment manifest gets vault annotations
pointing to the right serviceAccountName.


### Manifest Hits API Server

Flux detects a new commit, runs kustomize build on the app folder,
combines all YAML files into one manifest, sends it to kube-apiserver.
(for Flux internals, see local-docs/signal-flows/flux.txt)

the API server runs 3 gates on EVERY object in the manifest:

    gate 1 — Authentication
      +-- who is sending this request?
      +-- for Flux: kustomize-controller's service account

    gate 2 — Authorization (RBAC)
      +-- is this identity allowed to create this resource type
          in this namespace?

    gate 3 — Admission Control
      +-- is the manifest valid? (schema validation)
      +-- do all registered webhooks pass?
      +-- this is where the vault injector webhook will fire later
          (on Pod objects specifically)

K8s handles basic ordering internally. the objects land in etcd:

    Namespace created first
      +-- ServiceAccount created
      +-- ConfigMap created
      +-- Secret (vault-ca) created
      +-- PVC created → NFS CSI provisions NAS directory
      |     (see nfs-k8s-pv-trace.md for the full storage path)
      +-- Service (ClusterIP) created → gets stable IP
      |     survives pod restarts, rollouts, delete/recreate
      |     only reachable inside cluster
      +-- Ingress object created → ingress-nginx controller picks it up
      |     (see web-request-aws-to-pod.md for the full ingress path)
      +-- Deployment created → saved to etcd


### Controller Manager — Deployment → ReplicaSet → Pods

controller manager watches kube-apiserver. it sees the new
Deployment:

    Deployment (replicas: 2, no ReplicaSet exists)
      |
      +-- controller manager creates ReplicaSet
      |     saved to etcd via kube-apiserver
      |
      +-- ReplicaSet needs 2 pods, has 0
      |     creates 2 Pod objects (no node assigned yet)
      |     saved to etcd → status: Pending
      |
      +-- Pod objects now exist in etcd but:
            no node assigned
            no containers running
            just a spec describing what SHOULD exist


### MutatingWebhook — Vault Agent Injector

as each Pod object is created, the API server checks registered
MutatingWebhooks before saving the final spec:

    vault-agent-injector-cfg webhook rule:
      +-- objectSelector: skip if app.kubernetes.io/name=vault-agent-injector
      |   (the injector doesn't inject itself)
      +-- forwards eligible Pod spec to vault-agent-injector service

    injector reads the pod's annotations:
      vault.hashicorp.com/agent-inject: "true"
        +-- enable injection (without this → pod returned unchanged)

      vault.hashicorp.com/role: "wordpress"
        +-- which Vault role to authenticate as

      vault.hashicorp.com/agent-inject-secret-db-creds: "secret/data/wordpress/config"
        +-- what secret path to fetch + filename to write

      vault.hashicorp.com/agent-inject-template-db-creds: |
          {{ with secret "secret/data/wordpress/config" }}
          DB_HOST={{ .Data.data.db_host }}
          DB_PASSWORD={{ .Data.data.db_password }}
          {{ end }}
        +-- how to render the secret (required — without it, Vault dumps
            the raw KV v2 API response including metadata wrapper)

      vault.hashicorp.com/tls-secret: "vault-ca"
        +-- K8s Secret containing IPA CA cert, mounted at /vault/tls/
        +-- NOT agent-extra-secret (that mounts at /vault/custom/ — wrong path)

      vault.hashicorp.com/ca-cert: "/vault/tls/ca.crt"
        +-- tells vault-agent where to find the CA cert for TLS verification

    injector mutates the pod spec — adds:
      +-- vault-agent-init (init container, prepended first in the list)
      +-- vault-agent (sidecar container, runs alongside app)
      +-- emptyDir volume at /vault/secrets/ (shared between all containers)
      +-- /vault/tls/ volume mount (from vault-ca Secret)

    mutated spec returned to kube-apiserver → saved to etcd

    template gotchas learned from TS:
      +-- hyphenated keys break Go templates silently:
          .Data.data.login-password parses as .Data.data.login MINUS password
          must use: index .Data.data "login-password"
      +-- {{- trim markers inside YAML annotations conflict with YAML parser
          remove them — use {{ only
      +-- key names must exactly match Vault — mismatch renders <no value>
          with no error


### Scheduler — Node Assignment

scheduler watches kube-apiserver. sees 2 pods with no node assigned:

    for each pod:
      |
      +-- Filtering stage — removes nodes that don't qualify:
      |     not enough CPU/memory → removed
      |     taint not tolerated → removed
      |     anti-affinity violated → removed
      |     node selector not matched → removed
      |
      +-- Scoring stage — picks best node from remaining
      |     considers: resource balance, existing pod spread, affinity weights
      |
      +-- writes node name into pod spec
            sent to kube-apiserver → saved to etcd
            status: Scheduled (still no containers running)


### Kubelet — Starting the Pod

kubelet on the assigned node watches kube-apiserver. sees a pod
scheduled to its node:

    kubelet reads full mutated pod spec
      |
      +-- writes /etc/resolv.conf inside the pod:
      |     nameserver 10.96.0.10 (kube-dns Service ClusterIP)
      |     search default.svc.cluster.local svc.cluster.local cluster.local
      |
      +-- containerd pulls container images (if not cached on node)
      |
      +-- init containers run IN ORDER (not simultaneously)


### Init Container 1 — vault-agent-init (Secret Fetch)

this is the most complex step. two separate TLS handshakes
happen, each using a different CA:

    vault-agent-init starts
      |
      +-- reads SA token mounted at /var/run/secrets/.../token
      |     (K8s auto-mounts a JWT for the pod's service account)
      |
      +-- resolves vault.lab.local via DNS
      |     (see coredns-resolution-chain.md — hosts plugin returns
      |      10.0.62.100 directly, FreeIPA never contacted)
      |
      +-- TLS connection 1: vault-agent → Vault cluster
      |     ─────────────────────────────────────────────
      |     URL: https://vault.lab.local:8200
      |     Vault presents: /opt/vault/tls/tls.crt (FreeIPA CA signed)
      |       SAN includes vault.lab.local (added after VIP cert incident,
      |       see vault-unseal-kms-chain.md)
      |     vault-agent verifies using: /vault/tls/ca.crt
      |       (IPA CA cert, mounted from vault-ca K8s Secret)
      |     result: encrypted channel to Vault established
      |
      +-- POST /v1/auth/kubernetes/login
      |     body: { role: "wordpress", jwt: <SA token> }
      |
      +-- Vault receives login request
      |     extracts SA name + namespace from JWT
      |     needs to verify the JWT is real — calls K8s back
      |
      +-- TLS connection 2: Vault → K8s API (TokenReview)
      |     ──────────────────────────────────────────────
      |     URL: https://10.0.51.100:16443
      |     K8s API presents: apiserver.crt (K8s internal CA signed)
      |     Vault verifies using: kubernetes_ca_cert (K8s CA cert,
      |       passed during one-time trust setup)
      |     Vault authenticates itself: presents vault-auth token
      |     result: encrypted channel to K8s API established
      |
      +-- Vault sends TokenReview request:
      |     "is this JWT valid? who does it belong to?"
      |
      +-- K8s API checks:
      |     is vault-auth allowed to review tokens?
      |       (yes — system:auth-delegator ClusterRoleBinding)
      |     is the JWT valid and not expired?
      |     what SA + namespace does it belong to?
      |
      +-- K8s responds: "yes, it's wordpress-sa in apps namespace"
      |
      +-- Vault matches SA + namespace against configured roles:
      |     role "wordpress" bound to SA=wordpress-sa, NS=apps → match
      |
      +-- Vault issues temporary token with wordpress-policy attached
      |     TTL configured in the Vault role (default 1h)
      |
      +-- vault-agent-init uses token:
      |     GET /v1/secret/data/wordpress/config
      |     Vault checks policy → read allowed → returns secret data
      |
      +-- renders template → writes /vault/secrets/db-creds
      |     file contains the rendered output (env vars, config, etc.)
      |
      +-- exits 0 — init container done

    the two TLS connections use DIFFERENT CAs:
      connection 1 (pod → Vault):  verified by FreeIPA CA
      connection 2 (Vault → K8s):  verified by K8s internal CA
    these are completely independent PKIs that don't trust each other.


### Init Container 2 — wait-for-dependency (If Present)

some apps have a second init container that waits for a dependency:

    wait-for-mariadb (WordPress example):
      +-- resolves mariadb-svc.database.svc.cluster.local
      |     (CoreDNS kubernetes plugin → kube-apiserver → etcd → ClusterIP)
      +-- nc -z mariadb-svc.database.svc.cluster.local 3306
      +-- loops every 2s until port open
      +-- exits 0 when MariaDB ready

    this ensures the app doesn't start before its database is reachable.
    all init containers must exit 0 before main containers start.


### Main Containers Start Simultaneously

once all init containers are done:

    app container (e.g. WordPress):
      +-- checks /vault/secrets/db-creds exists
      +-- export $(cat db-creds | xargs) → loads as env vars
      +-- exec docker-entrypoint.sh
      +-- entrypoint reads env vars → generates config (wp-config.php)
      +-- app starts and listens

    vault-agent sidecar (runs alongside, not init):
      +-- runs its OWN auth flow (separate from init container)
      +-- gets its OWN vault token
      +-- watches Vault for secret changes
      +-- if secret changes in Vault → re-renders /vault/secrets/db-creds
      |   automatically (~4.5 minutes detection)
      |   no pod restart needed
      +-- renews its token before TTL expires → loops forever


### Probes and Service Registration

kubelet runs probes on the app container:

    liveness probe — is the process alive?
      +-- e.g. GET /wp-includes/images/blank.gif (local file)
      +-- fail → kubelet restarts the container
      +-- does NOT remove from Service endpoints (restart first)

    readiness probe — is the app ready to serve?
      +-- e.g. GET /wp-content/index.php (NFS mount — tests storage too)
      +-- or tcpSocket port 3306 (MariaDB — no auth needed, TCP check)

    readiness pass:
      +-- kubelet reports pod Ready to kube-apiserver
      +-- kube-apiserver saves pod status + pod IP to etcd
      +-- endpoint controller (in controller manager) watches
      +-- updates Service endpoints to include this pod
      +-- pod now receives traffic via Service ClusterIP

    readiness fail:
      +-- pod removed from Service endpoints
      +-- no traffic routed to it
      +-- pod stays running — not killed, just excluded


### The vault-ca Secret — How IPA CA Gets Into Pods

vault-agent runs inside a container. it doesn't have access to
the host's /etc/ipa/ca.crt. so the IPA CA cert is delivered via
a K8s Secret:

    vault-ca Secret (per namespace):
      apiVersion: v1
      kind: Secret
      metadata:
        name: vault-ca
        namespace: <app-namespace>
      stringData:
        ca.crt: |
          -----BEGIN CERTIFICATE-----
          <FreeIPA CA certificate content>
          -----END CERTIFICATE-----

    the annotations on the pod tell the injector to mount it:
      tls-secret: "vault-ca"  → mounts Secret at /vault/tls/
      ca-cert: "/vault/tls/ca.crt" → tells agent where to find it

    must exist in EVERY namespace where vault injection is used.
    each app namespace has its own copy: vault-ca-secret.yaml.
    (apps, database, monitoring, alertmanager, remediation,
    etcd-backup, nginx-test)


### StatefulSet Variation

StatefulSets follow the same flow above with key differences:

    ordered creation (not parallel):
      +-- pods created ONE AT A TIME in order
      +-- mariadb-0 must be Running + Ready before mariadb-1 starts
      +-- guarantees primary is up before replicas

    stable identity:
      +-- pod name is STABLE: mariadb-0 (not random hash like Deployments)
      +-- pod dies → recreated with SAME name: mariadb-0
      +-- enables stable DNS per pod:
            mariadb-0.mariadb.database.svc.cluster.local

    two services instead of one:
      +-- headless Service (clusterIP: None, name: mariadb)
      |     no load balancing — enables per-pod stable DNS
      |     StatefulSet requires this — linked via spec.serviceName
      +-- ClusterIP Service (name: mariadb-svc)
            used by apps: mariadb-svc.database.svc.cluster.local
            load balances across healthy pods (readiness probe)

    PVC per pod (not shared):
      +-- volumeClaimTemplate auto-creates PVC per pod:
      |     name formula: <template-name>-<statefulset>-<ordinal>
      |     e.g. mariadb-data-mariadb-0
      +-- PVC survives pod deletion:
      |     mariadb-0 deleted → PVC stays
      |     mariadb-0 recreated → reattaches to same PVC
      |     data preserved across restarts
      +-- PVC survives StatefulSet deletion → must delete manually
      +-- volumeClaimTemplate is immutable → must delete StatefulSet +
          PVC to change storageClass (always backup first)
      +-- reclaimPolicy: Retain → PV goes Released on PVC deletion
          → NAS data untouched

    rolling update differences:
      +-- pods updated in REVERSE order: last pod first, mariadb-0 last
      +-- each pod must be healthy before next is updated
      +-- safer for databases — primary updated last

    MariaDB-specific config:
      +-- securityContext fsGroup: 999 → sets NFS volume ownership to
          mysql group so MariaDB process can write
      +-- --innodb-flush-method=fsync (NFS compatibility)
      +-- --general-log=1 --general-log-file=/dev/stdout (Loki picks up)
      +-- --slow-query-log=1 --long-query-time=2 (slow query detection)


### Rolling Update (Deployment)

when the deployment manifest changes in Git:

    Flux detects change → sends updated Deployment to kube-apiserver
      +-- pod template changed → controller manager triggers rolling update
      +-- create 1 new pod → full flow above repeats
      +-- wait until new pod Ready
      +-- delete 1 old pod
      +-- repeat until all pods replaced
      +-- at least 1 pod always Running → zero downtime

    changes that trigger rolling update:
      image version, env vars, resource limits, command,
      volume mounts, probe configuration

    changes that do NOT trigger rolling update:
      replicas count (scale only), Deployment metadata labels
      outside the template block


### Volumes in Final Pod

    Deployment (WordPress example):
      +-- wordpress-data → PVC (NFS, /var/www/html/wp-content)
      +-- php-config → ConfigMap (/usr/local/etc/php/conf.d/uploads.ini)
      +-- /vault/secrets/ → emptyDir (injector added, shared between all containers)
      +-- /vault/tls/ → Secret vault-ca (injector added, ca.crt for TLS)

    StatefulSet (MariaDB example):
      +-- mariadb-data → PVC per pod (NFS hard mount, /var/lib/mysql)
      +-- /vault/secrets/ → emptyDir (injector added)
      +-- /vault/tls/ → Secret vault-ca (injector added)


### Token Lifecycle and Leak Risk

vault tokens issued to pods:

    TTL configured in the Vault role (default 1h)
    token lives only inside the pod's filesystem
      +-- never in logs
      +-- never in env vars
      +-- not visible from outside without exec access

    if token is stolen:
      anyone with it can read the scoped secrets until expiry.
      BUT to steal it you need to exec into the pod or compromise
      the node — at which point you already have direct access to
      the mounted secret files at /vault/secrets/.
      the token theft doesn't give you anything you couldn't already
      read directly. theoretical risk in practice.


### Known Gaps

1. vault-auth token is long-lived (30000h ≈ 3.4 years)
     if compromised, valid for years. no rotation mechanism.
     to revoke: create a new token, update auth/kubernetes/config.
     manual operation. accepted — token only allows TokenReview API
     calls, which is read-only. not a high-value target.

2. no bound_cidrs on issued pod tokens
     vault tokens issued to pods are not IP-bound. if exfiltrated,
     they work from anywhere until TTL. can add bound_cidrs to the
     Vault role to restrict to pod IP ranges. not configured.
     accepted for current scale.

3. vault-injector blocked in kube-system namespace
     admission webhook restriction — vault agent injection is
     blocked in kube-system by default. hit during remediation pod
     setup — drove the decision to use a dedicated remediation
     namespace instead. documented in TS-K8S-017.

4. vault-ca Secret must exist per namespace
     if vault-ca Secret is missing from a namespace, vault-agent
     can't verify Vault's TLS cert → init container fails → pod
     stuck in Init state. no automated mechanism to ensure the
     Secret exists — it's a manual YAML file per namespace.

5. template rendering errors are silent
     key name mismatches in Go templates render <no value> with
     no error. vault-agent-init exits 0, secret file is written
     with wrong content, app starts and fails when it reads the
     value. requires checking the rendered file content, not just
     the exit code.
